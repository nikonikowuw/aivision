# 个人中心资料与密码修改

## Goal

为已登录用户提供可用的个人中心，使用户能够查看并修改本人资料，并在验证旧密码后修改登录密码；所有操作只能作用于当前认证用户，不能借此修改角色、状态、部门或其他账号。

## Background

- 账户下拉菜单已能进入个人中心，现有页面位于 `ui/apps/web-antd/src/views/_core/profile/`。
- 基本设置目前仅调用 `GET /api/user/info` 回填表单，未处理提交；角色选项是模板模拟数据。
- 修改密码页面仅显示成功提示，没有调用后端。
- `GET /api/user/info` 是登录态/导航使用的精简契约，只返回 userId、username、realName、roles、avatar、desc、homePath，不包含邮箱和手机号。
- 用户模型已有 nickname、email、phone、avatar、remark 字段。
- `PUT /api/user/:id` 是受 `system:user:edit` 权限保护的管理员接口，不应复用于普通用户修改本人资料。
- 当前项目没有头像文件上传接口或对象存储约定。

## Requirements

- R-1：个人资料读取与保存必须从认证上下文获取当前用户 ID，不接受客户端指定目标用户 ID。
- R-2：首版允许修改昵称、邮箱、手机号和个人简介；用户名只读，角色、状态和部门不在表单中展示或提交。
- R-3：头像首版仅展示现有值，不提供修改能力，不新增上传接口或存储方案。
- R-4：保存成功后必须同步刷新前端用户状态，使页头昵称和个人中心摘要立即更新。
- R-5：首版提供密码修改，必须校验旧密码；新密码必须符合后端长度规则且两次输入一致。
- R-6：资料与密码接口继续使用统一 `{code,data,message}` 响应和现有认证中间件。
- R-7：本人资料与密码写接口必须显式登记为“已认证用户可写”，不能要求管理员权限，也不能被权限中间件的默认拒绝规则拦截。
- R-8：表单加载、提交、失败和成功状态应有明确反馈，并防止重复提交。
- R-9：个人中心首版只保留“基本设置”和“修改密码”标签，移除未接入业务的静态“安全设置”和“新消息提醒”。
- R-10：修改密码成功时，密码更新与该用户全部 Refresh Token 吊销必须在同一数据库事务中完成；前端随后清理会话并返回登录页，要求用户使用新密码重新登录。
- R-11：当前无状态 Access Token 不新增黑名单机制，已签发的 Access Token 最多继续有效到既有短期过期时间。

## Out of Scope

- 用户自行修改角色、状态、部门、用户名或头像。
- 头像上传与文件/对象存储能力。
- “安全设置”和“新消息提醒”业务能力。
- 管理员用户管理接口行为调整。

## Acceptance Criteria

- [ ] 普通已登录用户能读取且只能更新本人的获准资料字段。
- [ ] 修改资料后重新请求用户信息以及刷新页面，显示持久化后的值。
- [ ] 用户不能通过请求体或路径参数修改角色、状态、部门、用户名或其他用户资料。
- [ ] 使用错误旧密码不能修改密码；正确旧密码与合法新密码可以修改，之后新密码可登录且旧密码不可登录。
- [ ] 密码修改成功后，该用户全部 Refresh Token 均被吊销，当前前端退出到登录页；密码更新和令牌吊销不会出现部分成功。
- [ ] 个人中心只显示“基本设置”和“修改密码”，所有新增用户可见文案支持 zh-CN、en-US、zh-TW。
- [ ] 未登录请求返回统一 401 响应。
- [ ] 后端相关测试、`make vet`、`make test` 通过；前端 `pnpm check` 及相关测试通过。

## Risks and Deferred Items

- 无状态 Access Token 不在本任务中引入黑名单；改密后其他设备已持有的 Access Token 最多继续有效到既有过期时间。
- 头像修改延后到具备明确上传与存储方案的后续任务。
