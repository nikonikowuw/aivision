# 网络配置服务

## Goal

允许有权限的管理员在管理后台查看并配置当前边缘设备的网络，而无需登录设备执行 SSH 命令。MVP 聚焦 DHCP 与静态 IPv4，静态配置包含 IP 地址、子网掩码或前缀、默认网关和 DNS。

用户价值：降低工厂现场部署和改网时的运维门槛，同时让高风险的宿主机网络变更具备权限控制、参数校验、结果反馈和操作审计。

## Background / Confirmed Facts

- 用户在本次请求中明确指出当前系统缺少网络配置服务；早期产品讨论也明确要求管理员能从 Web 端配置边缘设备网络，不依赖运维人员操作系统命令。
- 当前仓库没有网卡枚举、IP/DNS/网关读取、网络状态或宿主机网络写入相关的后端接口、数据模型和前端页面。现有业务路由集中在 `app/internal/router/router.go:102`，前端动态菜单通过 `/menu/all` 加载。
- 这是跨前后端功能：后端负责宿主机网络能力、校验、授权、审计和统一错误；前端负责状态展示、配置表单、风险确认和结果反馈。
- 产品 PRD 要求“系统配置”写操作进入现有操作日志，并沿用当前 RBAC 菜单树；权限码采用 `<domain>:<resource>` / `<domain>:<resource>:<action>` 形式，见`docs/prd/ai-video-analytics-edge-platform-v1.0.md:687`。
- 当前活动的 `08-22-cpp-engine-skeleton-macos` 任务明确不修改 `app/` 和前端，且没有 parent/child 关系；本任务是独立任务，不作为该 C++ 引擎任务的子任务。
- Linux 共同的内核控制面是 `NETLINK_ROUTE` / rtnetlink：可读取和修改网卡、IP 地址及路由，相关修改需要 `CAP_NET_ADMIN`；它不提供 DHCP 客户端或跨重启持久化。
- macOS 的正式配置面是 SystemConfiguration：`SCPreferencesCommitChanges` 写入持久化配置，`SCPreferencesApplyChanges` 应用到运行系统。

## Key Decisions

- **D1 首版平台**：首版同时交付 Linux 与 macOS 的网络读取和写入能力。
- **D2 Linux 可移植层**：Linux 不以任何发行版网络管理服务为统一抽象；链路、地址和路由的共同底层使用 rtnetlink。DHCP 与持久化不能伪装成 rtnetlink 能力，必须另行明确所有者。
- **D3 macOS 配置层**：macOS 使用 SystemConfiguration 的网络 Service / Protocol 与 SCPreferences commit/apply 语义，不通过解析 `ifconfig` 或 `networksetup` 文本作为主实现。
- **D4 Linux 网卡所有权**：本系统是被管理有线网卡的唯一配置所有者。部署 Profile 负责让其他网络管理器忽略该网卡；本模块负责 DHCP、静态 IPv4、配置持久化和开机恢复。“独占”仅指配置所有权，其他应用仍可正常通过该网卡通信。
- **D5 安全应用协议**：所有写操作先作为候选配置应用，保留可恢复的旧配置，并启动 120 秒确认窗口。管理员确认后，候选配置才成为正式基线；超时、应用失败或负责进程在待确认状态下重启时，自动恢复旧配置。为支持崩溃恢复，可以持久记录旧快照、候选值和截止时间；macOS 也允许按 SystemConfiguration 要求先 commit 候选值再 apply，但在用户确认前始终属于可回滚的待确认事务。Linux 与 macOS 对外语义一致。
- **D6 MVP 网络范围**：Linux 支持一个或多个被本系统接管的物理有线网卡；macOS 支持已有 Ethernet 与 Wi-Fi Network Service 的 IPv4 参数，不负责 Wi-Fi 关联。两端均支持 DHCP、静态 IPv4、掩码/前缀、默认网关和 DNS；IPv6 与高级网络能力延后。
- **D7 权限模型**：Go API 主进程在 Linux 与 macOS 上直接以 root 身份运行，网络平台实现与 120 秒事务协调均位于该进程内，不增加特权 helper。作为风险补偿，网络写入只能通过类型化内部 API 到达平台实现，禁止提供任意命令、路径或脚本执行入口。
- **D8 配置恢复**：每个可管理接口具有不可变出厂基线和最后有效配置。Linux 出厂基线由部署 Profile 提供，缺省为 DHCP/DNS 自动；macOS 在首次接管时快照已有 SystemConfiguration 配置。确认配置使用原子替换、单调版本和校验和保存。启动校验失败时先恢复最后有效配置，再失败则恢复出厂基线；显式恢复出厂保留操作日志。
- **D9 单一主出口**：整机同一时刻最多只有一个主出口接口。主出口提供整机非作用域默认
  路由和系统默认 DNS；其他受管接口只提供地址、子网和直连路由。切换主出口时，新接口
  提升、旧接口降级以及共享默认路由/DNS 的迁移属于同一个 120 秒候选事务。
- **D10 部署边界**：网络写入首版只支持具备宿主机网络能力的原生 Linux/macOS root 进程。
  当前 Alpine 容器镜像默认关闭 cgo，Compose 未授予 host network、`NET_ADMIN`/`NET_RAW`、
  resolver 或 root-only 状态目录，因此默认容器部署不属于网络能力支持矩阵；在该形态下服务
  必须在监听前或能力检查时明确 fail closed，不得退回 shell 或静默只改数据库。
- **D11 导航归属**：网络配置归入“运维管理”下的 `Network` 页面，使用 `/ops/network`、
  `OpsNetwork`、`routes.ops.network` 和 `ops:network` 权限域。系统管理继续只承载用户、
  角色、菜单、部门和操作日志；操作日志动作文案仍沿用现有 `system.log.*` 命名空间。

技术依据：Linux [`rtnetlink(7)`](https://man7.org/linux/man-pages/man7/rtnetlink.7.html)；
Apple [`SCPreferencesCommitChanges`](https://developer.apple.com/documentation/systemconfiguration/scpreferencescommitchanges(_:))
与 [`SCPreferencesApplyChanges`](https://developer.apple.com/documentation/systemconfiguration/scpreferencesapplychanges(_:))。

## Requirements

### R1 网络状态

- R1.1 后端提供全部可管理网络接口及其当前有效状态，至少包含稳定标识、名称、类型、
  启用/连接状态、MAC、IPv4 获取模式、IPv4 地址、子网掩码或前缀、默认网关、DNS
  服务器列表、是否为主出口以及是否可由本系统写入。
- R1.2 Linux 只将被部署 Profile 标记为本系统所有的物理有线网卡列为可写；macOS 将已有
  Ethernet 与 Wi-Fi Network Service 列为可写，但不提供 Wi-Fi 扫描、关联或凭据修改。
- R1.3 状态以宿主机当前实际生效值为准；读取失败或字段不受当前平台支持时返回明确状态，
  不伪造空值或 `0` 为有效结果。

### R2 DHCP 与静态 IPv4

- R2.1 管理员可以把可写网络接口切换为 DHCP。主出口使用租约提供的地址、默认网关和
  DNS；非主出口只使用租约地址和前缀，租约中的默认网关和 DNS 不得成为整机默认值。
- R2.2 管理员可以提交静态 IPv4 地址和子网掩码或 CIDR 前缀。主出口还必须提交默认网关
  和一个或多个 DNS；非主出口不得提交整机默认网关或 DNS。
- R2.3 后端在触碰宿主机配置前完成格式和组合校验，包括合法 IPv4、合法掩码/前缀、
  地址与网关可达关系、合法且去重的 DNS 地址、主出口唯一性以及主/非主出口字段约束；
  校验失败时不得产生部分变更。
- R2.4 写操作先应用为候选配置并启动 120 秒确认窗口；成功响应必须基于候选配置的实际
  状态回读，不能只表示命令已提交。
- R2.5 整机最多一个接口标记为主出口；允许在无可用上联或隔离网络场景下暂时没有主出口，
  但只要存在整机默认网关或系统默认 DNS，就必须存在且只能存在一个主出口。
- R2.6 将非主出口提升为主出口时，旧主出口自动降级但保留自身地址、子网和直连路由；
  新旧接口状态、默认路由与 DNS 迁移必须作为一个候选事务提交、确认或整体回滚。
- R2.7 整机同一时刻最多存在一个待确认网络变更；这是因为默认路由与系统 DNS 是跨接口
  共享资源。待确认期间拒绝任何接口的新写操作或恢复出厂操作。
- R2.8 管理员在期限内确认后，候选配置才成为正式基线；超时、显式取消、应用失败或
  负责进程在待确认状态下重启时，自动恢复并回读旧配置。确认前允许持久记录旧快照、
  候选值和截止时间，但不得将候选状态误报为已确认配置。
- R2.9 平台在技术可行时于确认窗口内保留旧管理地址以维持管理链路；无法保留时，API
  必须返回新地址和确认截止时间，前端引导管理员从新地址重新连接确认。

### R3 权限、审计与错误

- R3.1 所有接口必须经过现有 JWT 与默认拒绝的权限中间件；页面读取权限和网络修改权限
  分离，权限码遵循项目既有命名规则。
- R3.2 每次修改无论成功或失败都进入现有操作日志，包含操作者、来源 IP、目标网卡、
  变更模式、脱敏后的变更摘要和结果；只读查询不记录操作日志。
- R3.3 API 沿用 `{code,data,message}`、`code=0` 成功契约；业务错误码和三语文案集中在
  `internal/pkg/errno`，内部命令、路径和堆栈不得返回前端。
- R3.4 root 权限不能绕过应用层边界：网络写入请求必须使用封闭的类型与枚举，网卡标识
  必须来自后端枚举出的可管理集合，禁止客户端传入命令、参数数组、文件路径或脚本文本。
- R3.5 网络事务日志和正式配置只允许 root 读写，使用固定目录、固定文件名、原子替换和
  明确权限；HTTP 静态文件服务及上传接口不得暴露该目录。
- R3.6 API 服务启动时若不是 root，必须在监听 HTTP 端口前失败并给出部署诊断；不得等到
  首次网络写入才暴露权限不足。

### R4 管理页面

- R4.1 在运维管理导航下提供网络配置页面，展示受支持网卡和当前有效配置。
- R4.2 页面提供 DHCP/静态 IPv4 模式切换和主出口选择；静态模式使用结构化输入控件并做
  即时基础校验，非主出口不显示或禁用默认网关和系统 DNS 输入。
- R4.3 选择新的主出口时，提交摘要必须同时显示旧主出口将被降级以及默认路由/DNS 将迁移，
  不能把该操作表现为单网卡局部修改。
- R4.4 提交前明确展示变更摘要、断连风险和 120 秒确认规则；提交期间防止重复操作，并
  区分成功、等待确认、已确认、已回滚、校验失败、权限不足、平台不支持和应用失败。
- R4.5 候选配置应用后，页面显示倒计时并提供确认与取消操作；连接中断时展示新地址，允许
  管理员从新地址重新打开页面完成同一待确认变更。
- R4.6 页面、菜单和错误以 `zh-CN`、`en-US`、`zh-TW` 对齐，页面权限接入后端动态菜单。

### R5 平台边界与可测试性

- R5.1 宿主机读取/写入能力与 HTTP 业务层隔离，通过统一接口提供 Linux、macOS 和测试
  实现；业务层不得拼接未经结构化约束的 shell 命令。
- R5.2 单元和 API 测试必须使用不会修改开发机真实网络的测试实现，覆盖读取、DHCP、静态
  配置、校验失败、平台失败、权限和审计行为。
- R5.3 首版同时支持 Linux 与 macOS，两个平台必须满足相同的业务 API 和验收语义；平台
  不支持的能力必须显式返回，不得静默降级。
- R5.4 Linux 的链路、地址和默认路由读写使用 rtnetlink；DNS 与本系统自有的 DHCP/
  持久化组件集成，不依赖某个发行版一定安装 NetworkManager、systemd-networkd、
  `ifupdown` 或特定命令行工具。
- R5.5 macOS 通过 SystemConfiguration API 读写已有 Network Service 的 IPv4 与 DNS
  Protocol，并分别执行持久化 commit 与运行态 apply。
- R5.6 Linux 部署 Profile 必须让 NetworkManager、systemd-networkd、ifupdown、ConnMan
  或厂商脚本停止管理受管网卡，并提供 root-only 所有权声明。运行时对已知管理器做检查并
  监听 rtnetlink 配置漂移；声明缺失、发现已知冲突或观测到外部覆盖时拒绝后续写入。
  不声称能够通用识别所有第三方脚本。
- R5.7 Linux 的 DHCP 客户端、配置持久化与开机重放由本系统拥有。网络平台实现和候选
  事务协调直接运行在 root Go API 进程中，不使用独立 helper。
- R5.8 Linux 与 macOS 实现优先使用结构化系统 API；不得通过 shell 解释器执行网络配置，
  不得根据 HTTP 输入拼接命令。两个平台的部署 Profile 必须明确 root 启动、配置目录权限
  和服务加固选项。
- R5.9 当前 `app/Dockerfile` 使用 `CGO_ENABLED=0`，`deploy/docker-compose.yml` 未提供
  宿主机网络、`NET_ADMIN`/`NET_RAW`、root-only 网络状态目录或 resolver 所有权；该默认
  容器形态不得声称支持网络写入。若未来提供特权 host-root 镜像，必须单独声明 cgo、能力、
  状态目录、Profile 和退出恢复条件，并通过 Linux/macOS 目标环境验收。

### R6 配置持久化与恢复

- R6.1 首次接管每个接口时创建不可变出厂基线。Linux 优先读取部署 Profile 声明，未声明
  时使用 DHCP/DNS 自动；macOS 快照该 Network Service 接管前的 IPv4 与 DNS 配置。
  基线还必须记录当时的整机主出口选择和共享默认路由/DNS 所有权。
- R6.2 每次用户确认候选配置后，以固定 root-only 路径、临时文件加原子重命名保存最后
  有效配置；记录单调版本、平台、稳定接口标识、主出口选择和内容校验和。
- R6.3 启动时校验事务日志、当前正式配置和最后有效配置。发现未完成候选事务先回滚；
  当前配置损坏时恢复最后有效配置，后者也损坏时恢复出厂基线，并记录恢复原因。
- R6.4 提供有修改权限的显式恢复出厂操作，按接口恢复出厂基线并走同一 120 秒确认协议；
  若基线包含主出口变化，则在同一事务中迁移共享默认路由/DNS。成功后清除该接口的候选
  事务和最后有效配置，保留出厂基线与操作日志。
- R6.5 出厂基线损坏或平台恢复失败属于不可自动掩盖的故障：接口标记为恢复失败，禁止继续
  写入，并返回可诊断但不泄露内部路径的错误。

## Acceptance Criteria

- [ ] AC1 有读取权限的管理员能在页面看到全部可管理接口及其类型、写入能力、当前实际
      IPv4 模式、地址、掩码/前缀、主出口状态、默认网关和 DNS。
- [ ] AC2 在 Linux 物理有线网卡以及 macOS 已有 Ethernet/Wi-Fi Network Service 上，
      DHCP 与合法静态 IPv4/DNS 配置均可成功应用并持久化；接口回读和页面刷新后显示
      宿主机实际生效值。多网卡场景只有主出口提供整机默认路由和系统默认 DNS，非主出口
      只保留地址、子网和直连路由。
- [ ] AC3 候选配置应用后进入 120 秒倒计时；期限内确认会将其提升为正式基线，页面和
      接口回读均显示已确认状态，重启后能够重放该配置。切换主出口时，新旧接口和共享
      默认路由/DNS 同时确认，不出现两个主出口。
- [ ] AC4 不确认、显式取消、模拟应用失败或在待确认阶段重启负责进程，均会恢复旧配置：
      静态模式精确恢复地址、掩码/前缀、网关和 DNS；DHCP 模式恢复自动获取并重新租约，
      不要求 DHCP 服务器分配相同 IP；主出口切换还必须恢复原主出口、默认路由和 DNS。
      重启后不存在悬空候选配置。
- [ ] AC5 非法 IP、掩码/前缀、网关或 DNS 组合返回明确业务错误，并证明宿主机配置未被
      部分修改；非主出口携带默认网关/DNS 或产生第二个主出口同样被拒绝。
- [ ] AC6 无修改权限的用户不能调用写入、确认或取消接口，直接构造请求同样返回 403；
      只有页面权限的用户只能查看。
- [ ] AC7 每次写入、确认、取消和自动回滚都生成可查询的操作日志，包含目标网卡、变更模式
      和脱敏摘要；只读查询不产生日志。
- [ ] AC8 页面在 DHCP 与静态模式间切换时字段启用状态正确，提交前显示断连风险，待确认
      状态显示倒计时，且所有可见文案在三种语言中都有对应键。
- [ ] AC9 Linux 部署验证覆盖所有权声明缺失、已知网络管理器仍托管和外部 rtnetlink
      漂移；三种情况均阻止后续修改并返回明确原因。
- [ ] AC10 安全测试证明客户端无法通过网卡标识或任意字段注入命令、路径或额外系统
      参数；网络配置/事务目录不可由非 root 用户或 HTTP 文件服务读写。
- [ ] AC11 API 服务以非 root 身份启动时，在监听端口前明确失败；以 root 启动时 Linux 与
      macOS 网络能力检查通过。
- [ ] AC12 篡改当前配置校验和后重启服务，会自动恢复最后有效配置；再同时破坏最后有效
      配置时，会恢复出厂基线并生成操作日志。
- [ ] AC13 显式恢复出厂走 120 秒确认协议；确认后网络恢复到 Linux Profile 基线或 macOS
      首次接管快照，候选事务被清除，既有操作日志仍可查询。
- [ ] AC14 出厂基线损坏或平台恢复失败时接口进入恢复失败状态，后续写操作被拒绝并返回
      明确业务错误。
- [ ] AC15 自动化测试不会触碰运行测试机器的真实网络，并覆盖 R5.2 所列行为。
- [ ] AC16 `app/` 的 `make vet`、`make test` 和 `ui/` 的 `pnpm check`、相关单元测试通过。

## Out of Scope

以下能力不纳入 MVP：

- IPv6、额外静态路由、VLAN、网桥、Bond、代理、防火墙和端口转发。
- 多默认出口、策略路由、ECMP、链路聚合和自动主备切换。
- Linux Wi-Fi 配置，以及 macOS 的 Wi-Fi 扫描、SSID/密码和关联管理。
- 多设备集中下发；当前范围只配置运行本系统的本机。
- 与网络配置无关的 NTP、存储清理和资源监控。

## Risks / Deferred

| Risk | Impact | Planning Response |
| --- | --- | --- |
| 候选配置使管理连接断开 | 管理员无法确认新配置 | 120 秒确认窗口；尽量保留旧地址，否则从新地址重连；未确认自动回滚 |
| 待确认期间进程或设备异常 | 候选配置可能被错误固化或旧配置丢失 | 持久记录恢复信息；启动时发现未完成事务立即回滚 |
| Linux 网卡所有权部署不完整 | rtnetlink 变更可能被其他管理器覆盖 | Profile 显式取消托管，运行时检测冲突并拒绝写入 |
| Linux 发行版和用户态组件差异 | 内核运行态控制可统一，但启动集成方式仍不同 | 本系统拥有 DHCP 与配置重放，Profile 只负责启动和网卡取消托管 |
| 主出口切换中断当前管理链路 | 默认路由和 DNS 的迁移可能使当前会话失联 | 整机事务快照 + 120 秒确认；返回候选地址；超时整体恢复旧主出口 |
| Go API 直接以 root 运行 | Web/API 漏洞可能获得完整宿主机权限 | 用户接受该部署取舍；强制类型化系统 API、默认拒绝权限、固定 root-only 配置目录、禁止 shell 与路径输入 |
| 配置文件或恢复元数据损坏 | 启动后网络状态不可预测 | 校验和 + 原子替换；最后有效配置与不可变出厂基线两级恢复；失败时停止写入 |
| CI 无法安全修改真实网络 | 端到端覆盖不足 | 平台接口测试替身 + 目标镜像隔离集成测试 |
