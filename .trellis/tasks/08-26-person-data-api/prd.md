# 人员数据与同步 API

## Goal

为父任务 `08-26-person-management` 提供 Go 侧人员业务事务和 API：统一管理人员、不可变注册图版本、人脸特征候选/激活版本，并让 RBAC 管理入口和白名单业务同步入口共享同一套一致性规则。

## Requirements

- 使用版本化 SQL 迁移建立人员、注册图版本、特征版本、索引版本及必要关联数据，不使用生产 AutoMigrate。
- V1.0 人员业务字段只包含 `person_id`、姓名和当前人脸照片，不建立部门、标签、分组或联系方式模型。
- 姓名必填但不唯一；重名人员以不同 `person_id` 独立存在，姓名不作为幂等键或关联键。
- 人员表使用内部 `id` 主键关联版本数据，但所有管理与同步 API 只使用业务主键 `person_id`；删除后同 `person_id` 重建生成新内部 `id`。
- `person_id` 设备内唯一且不可修改；页面可自动生成，业务同步入口必须提供并以其幂等操作。
- 管理 API 接受可选 `person_id`：缺省时由服务端生成，提供时在写入任何人员或异步作业前校验唯一；生成值与手工值使用同一字段和唯一约束。
- 人员不维护对外 `revision`；同字段使用后写覆盖，repository 必须做字段级更新，避免资料写入与异步人脸激活互相覆盖无关字段。
- 不持久化独立 `face_status`；当前注册照片引用是人脸是否已注册的唯一事实来源，API 由此派生 `has_face`，避免状态与照片关系不一致。
- 持久化 `feature_status=missing|ready|stale`，并记录特征的生产算法包、特征提取器 ID/版本、模型摘要和 `feature_contract_id`；无当前照片时固定为 `missing`，只有 `has_face=true` 且契约匹配当前激活算法包要求时才进入索引。
- 支持显式移除当前人脸并清空当前照片引用、切换 `feature_status=missing`；普通更新未携带照片动作时保持当前人脸不变。
- 人员建档与人脸注册使用两个独立原子命令；首次注册失败不回滚人员档案，并保持当前照片引用为空、`feature_status=missing`。
- 当前激活算法包要求的特征契约变更时，所有不匹配特征必须标记为 `stale` 并从新索引排除；仅算法包版本变化但契约相同不使特征失效，API 不得只依据特征字节存在或生产包版本判断可用性。
- 无照片建档和纯姓名更新不触发索引重建；首次注册、换图、显式移除人脸和删除当前可识别人员触发候选索引流程。
- 首次人脸注册、换图、显式移除人脸和删除当前可识别人员必须编排 C++ 注册/索引能力；只有数据库激活版本与引擎激活索引一致后才返回成功。
- 删除后不提供恢复；同一 `person_id` 可重新创建为新的内部记录，但必须重新注册照片和提取特征，不能复用已删除版本的数据。
- 候选操作失败时保留旧人员版本、旧照片、旧特征和旧索引。
- 提供 RBAC 管理 API、默认拒绝的 IP 白名单同步 API、分页查询和稳定业务错误码。
- 管理 API 中修改姓名、补录、换图和移除人脸统一校验 `resource:person:update`，不定义独立人脸权限。
- 新增、编辑、删除接口分别校验 `resource:person:create`、`resource:person:update`、`resource:person:delete`；前后端不依赖仅隐藏按钮实现授权。
- IP 白名单运行时配置存入数据库，默认空列表；提供受 `resource:person:sync-config` 保护的查询与增删接口，修改立即生效并写操作日志。
- 部署配置只允许首次初始化白名单，不覆盖已有数据库配置。
- 外部同步同时提供单人员幂等接口和批量接口；所有已完成特征准备的索引变更进入统一协调器，按数量阈值或最长等待时间合并构建候选索引。
- 批量请求是显式 `upsert|delete` 命令集合而非全量镜像；未出现在请求中的现有人员保持不变，只有 `delete` 改变删除状态。
- 管理页面和业务系统共享同一模型但不存在来源权威关系；服务保证操作和索引一致性，不承诺跨系统自动收敛。
- 一个业务批次的合法索引变更作为不可拆分提交组且最多参与一次全量构建；多个提交组允许共同刷新。
- 协调器阈值从运行平台 Profile 读取；先使用 macOS 实测值验证，RK3576 后续独立覆盖，业务服务不写死数值。
- 批量接口逐项校验并返回逐项结果；非法项可失败，合法纯资料项可独立成功，所有合法索引变更作为一个原子组提交或回滚。
- 平台为每次批量提交生成执行 `batch_id`；业务系统无需提供或关联批次 ID，可以在修正部分图片后完整重发人员集合。
- 完整重发形成新的不可变批次记录；服务逐人比较资料和注册处理指纹，未变化项返回 `changed=false`，不重复进入 C++ 或索引协调器。
- 批量处理使用异步作业；提交返回 HTTP `202`，批次汇总与逐项结果分别查询。
- 所有影响索引的单人员操作同样异步，返回 `operation_id` 并复用批次作业状态、幂等和重启恢复机制；纯资料写入保持同步。
- 外部单人员写请求要求唯一 `request_id`，持久化载荷摘要和原结果/操作；同键同载荷重试复用，同键不同载荷冲突。
- 异步操作成功后才切换人员状态，失败时保持提交前的激活版本。
- 所有入口共享每人员一个进行中索引操作的持久化互斥；冲突返回现有 `operation_id`，不排队、不取消、不抢占。
- 暂时性图片下载、网络和引擎错误最多自动退避重试 3 次；确定性校验、质量、版本和超限错误立即终止，重试不生成新操作标识或副作用。
- 每个输入项要求批次内唯一 `person_id`，重复时在创建作业前拒绝整批；逐项结果以 `person_id` 关联，并包含状态、阶段、稳定错误码、消息、可重试标识，以及最终 `has_face` 和 `feature_status`。
- 单批最多 10,000 项，超过上限时整批拒绝；后台 worker 使用受控并发，不能按请求项目数创建无界 goroutine 或并行 C++ 调用。
- 可选 `client_ref` 只原样回传，不参与唯一性或幂等；每项仅允许一个 `upsert|delete` 最终操作，`upsert` 明确使用 `keep|replace|remove` 人脸动作。
- `upsert` 的资料和人脸子操作独立提交；只完成资料时返回 `partially_succeeded` 和两个子结果。
- 批量项目使用局域网可访问的 `photo_url`；异步作业负责受限下载，不支持 multipart 暂存或 JSON Base64 照片。
- 单项照片下载失败或超限只影响该项目，并在逐项结果中返回下载阶段错误。
- 图片下载后计算 SHA-256，并结合 `feature_contract_id` 和质量策略版本做普通注册结果去重；生产算法包版本不参与兼容性指纹。相同指纹成功项返回 `changed=false`，不调用 C++ 重复提取或进入索引协调器，显式强制提取除外。
- 可选 `photo_sha256` 与实际内容不一致时项目失败；仅 URL、文件名或 ETag 相同不能跳过处理。
- MVP 外部同步只校验调用方 IP 白名单，通过后信任其 HTTP/HTTPS `photo_url`，不增加图片目标白名单；认证组件需可替换，以便后续新增 Token 策略而不修改人员业务服务。
- URL 下载保留超时、最大响应大小和真实图片类型校验等基本运行边界。
- 管理页面使用人员专用 multipart 接口上传不超过 10 MiB 的 JPEG/PNG；接口校验真实类型并创建异步注册操作，不复用通用文件上传业务结果。
- 提供受 `resource:person:update` 保护的重新提取接口：仅对具有当前有效注册照片的人员创建异步操作，强制跳过成功指纹复用并基于当前照片产生新特征候选版本。
- 重新提取复用每人员一个进行中索引操作的互斥、持久化状态、重试策略和统一索引协调器；失败不改变当前激活特征。
- 重新提取请求明确记录 `scope=single|selected|all`、目标算法包版本和 `feature_contract_id`；目标可为当前、候选或仍可加载的历史版本，范围与目标独立，三种范围均强制处理且返回异步任务或操作 ID 与分页逐项结果。
- 强制提取任务另行记录可选算法激活/回切计划；没有激活计划时只生成目标版本特征，不改变当前算法。只有关联计划的 `all` 范围任务才使用固定初始快照与增量追平并进入原子激活流程。
- 算法包安装或选择历史版本时读取其声明的特征提取器 ID/版本、模型摘要和兼容性字段，并按规范化字段与实际模型文件 SHA-256 重算 `feature_contract_id`；声明不一致时拒绝安装/加载，运行时结果契约不一致时拒绝持久化。目标契约与当前契约相同不强制全量迁移，不同则激活计划必须绑定全量强制提取任务。
- 历史算法包安装记录默认保留，不执行自动清理；提供管理员显式删除能力，并在删除前原子检查当前激活、候选和待处理/进行中任务引用，存在任一运行依赖时返回稳定冲突错误。
- 历史特征的生产来源引用不阻止删除无运行依赖的包文件；删除后继续保留算法包 ID/版本、提取器、模型摘要和契约审计字段，并标记该版本当前不可用于提取。重新安装同版本时按新安装重新校验。
- 重提取失败时，旧特征仅在匹配当前激活算法和契约时保持 `ready`；不匹配旧特征继续为 `stale`，不得因任务失败被错误恢复。
- 任一时刻最多一个全量特征迁移任务运行；worker 有界并发处理固定快照，所有新特征仅作为候选版本保存，不能逐人覆盖激活特征或逐人重建索引。
- 新算法及其 `feature_contract_id` 先持久化为候选版本；候选安装和全量迁移期间，当前激活算法、人员 `feature_status`、激活特征引用和激活索引版本保持不变。
- 候选版本满足激活条件后，在数据库事务与引擎激活协议中原子切换目标算法、目标特征引用和索引版本；成功后旧契约特征标记为 `stale`，失败时完整旧版本继续有效。
- 全量迁移允许人员级失败；成功候选特征保留复用，后续修正失败人员时只处理失败项，不重新提取成功人员；激活后的任务结果统一使用 `activated|activated_with_errors`。
- 全量迁移存在人员级失败时仍自动激活成功人员的候选完整索引；失败人员保留当前照片但切换为 `feature_status=stale` 并退出索引，后续换图或重新提取成功时恢复为 `ready`。
- 候选一致性校验成功后，任务编排器无人员失败时进入 `activated`，有人员失败时进入 `activated_with_errors`；不建立 `awaiting_activation_confirmation` 状态或人工部分激活接口。
- 最终写屏障前失败人员换图时，变更事务把新照片版本写入原迁移任务的增量集合并重新打开该人员项目；仅该项目按目标算法重试，其他成功候选特征和项目结果保持不变。任务激活后换图创建当前算法下的普通异步操作。
- 同一照片指纹的确定性失败直接复用原结论；照片版本变化或失败为可重试运行故障时重新处理。人员级失败不阻止激活，算法加载、契约、候选索引构建、版本一致性或原子切换失败则终止候选激活并保持旧版本。
- 最终增量水位存在 `has_face=true` 人员但目标契约 `ready` 数为 0 时触发稳定零成功保护错误，任务失败且不切换激活版本；最终水位没有注册人脸时允许激活空索引。
- 全量任务创建时持久化初始人员/照片版本快照和数据库变更水位；初始总数不随迁移期间写入变化，任务结果另行统计待追平增量。
- 迁移期间人员新增、首次注册、换图、移除人脸和删除的成功事务必须追加持久化迁移增量；同一人员多次变化按最新当前照片版本折叠，服务重启后仍可继续追平。
- 激活前建立短暂全局索引写屏障，拒绝新的索引相关人员写请求并返回稳定可重试错误；处理完截止水位内增量后生成最终完整候选快照并执行算法、特征引用和索引原子切换，随后解除屏障。
- 逐项结果使用服务端分页并支持按状态筛选，不在单次响应中返回 10,000 项或任何照片/特征字节。
- 为管理端提供只读批次记录查询：支持按提交时间和批次状态筛选汇总，并在指定批次内按 `person_id`、项目状态分页查询逐项结果；返回来源 IP，但不返回照片、特征或请求敏感载荷。
- 批次结果只提供轮询查询，不实现完成回调、回调鉴权或投递重试。
- 写操作接入操作日志，图片、特征和敏感载荷不得进入日志正文。

## Acceptance Criteria

- [ ] 页面 API 与同步 API 操作同一人员模型，重复 `person_id` 同步不产生重复数据。
- [ ] 页面建档省略 `person_id` 时服务端生成唯一值；提供重复值时无人员、照片、操作或索引副作用。
- [ ] 空姓名被稳定校验错误拒绝，不同 `person_id` 使用相同姓名时可分别创建、查询和更新。
- [ ] 并发资料与人脸操作按字段更新，同字段后写覆盖，不发生姓名与人脸引用之间的丢失更新。
- [ ] 无照片人员可成功建档但不进入索引；首次注册失败保留当前照片引用为空、`feature_status=missing` 的档案；人脸注册、换图和删除成功返回时，引擎识别状态已经生效，失败时旧激活版本保持不变。
- [ ] IP 白名单支持 IPv4、IPv6 单地址和 CIDR，默认不信任 `X-Forwarded-For`。
- [ ] 白名单数据库配置即时生效、默认拒绝、权限受控且可审计，重启后保持；初始化配置不会覆盖运行时修改。
- [ ] 批量同步和单人员操作不会逐人重建全量索引；协调器按数量/时间策略合并刷新，并能把最终索引版本关联回各操作与批次结果。
- [ ] 混合成功、字段失败、照片失败和索引组失败场景均返回稳定逐项结果，且不会产生半激活索引。
- [ ] 批次结构重复被整批拒绝；同一项目资料成功、人脸失败时数据库状态与 `partially_succeeded` 子结果一致。
- [ ] 10,000 项批次可接受并以有界并发处理，10,001 项在任何照片下载或业务写入前拒绝。
- [ ] 批次状态与逐项结果可跨服务重启恢复；每次重新提交生成新批次，但注册处理指纹相同的成功项不重复调用 C++ 特征提取或进入索引构建。
- [ ] 调用方可通过 `batch_id` 查询汇总，并通过分页结果按 `person_id` 准确定位每个失败或回滚项、失败阶段与原因，可选 `client_ref` 原样返回。
- [ ] 单人员索引操作立即返回 `202`，可按 `operation_id` 查询，且不会因 HTTP 超时导致结果未知或重复执行。
- [ ] 单人员 `request_id` 幂等记录可跨重启恢复，响应丢失后的同请求重试不会生成第二个操作或额外版本。
- [ ] 页面、单人同步和批量项目并发修改同一人员时只启动一个索引操作；冲突项返回可重试错误和现有操作 ID，服务重启不释放未终止操作的互斥。
- [ ] 自动重试分类、次数、操作标识复用和终态 `retryable` 标记均有覆盖成功、耗尽及重启恢复的测试。
- [ ] 批量任务能从合法局域网 URL 下载照片；URL 不可达、超时、响应超限或类型不合法时仅对应项失败且响应正文不进入日志。
- [ ] 修正部分图片后完整重发不会让成功且未变化的人员重复提取或刷新索引；失败图片内容变化后能够重新处理，未变化的确定性失败可复用原结论。
- [ ] 全量、部分和单人员下发具有相同显式命令语义，遗漏人员不会被删除，页面/API 交替写入不会绕过操作级一致性保护。
- [ ] 管理端照片接口受 JWT/RBAC 保护，拒绝超限或伪造类型文件，并返回可查询的异步操作而不是同步等待特征提取。
- [ ] `resource:person:update` 同时授权人员资料和人脸维护接口，缺少该权限时两类写入均被拒绝。
- [ ] 已注册人脸人员可在不重新上传照片的情况下强制重新提取；操作返回 `202 + operation_id`，同指纹也会真实提取，失败后旧特征与旧索引保持激活。
- [ ] API 根据当前照片引用返回派生 `has_face`，并返回独立 `feature_status` 和特征契约；不持久化重复的 `face_status`。契约不匹配的旧特征标记为 `stale`，即使特征字节仍被保留也不能进入当前索引。
- [ ] 单人、选中和全量范围均返回可跨重启查询的异步结果并绕过成功指纹复用；算法全量迁移开始后的新增或变化人员不改变初始快照统计，而是作为可见、可恢复的增量集合在激活前追平。
- [ ] 一键全量可选择当前、候选或可加载历史算法包版本并强制处理每张当前照片；只有明确关联算法升级/回切计划时才切换算法，普通提取不会因目标是历史版本而改变全局状态。
- [ ] 算法包版本变化但 `feature_contract_id` 相同时可继续使用现有特征；契约变化时激活接口拒绝缺少全量迁移的计划，且每条新特征记录可追溯到提取器和模型摘要。
- [ ] 清单契约、平台重算指纹和运行时提取结果三者必须一致；任一不一致均返回稳定错误且不写入特征、候选索引或激活版本。
- [ ] 历史算法包不会被自动清理；运行依赖版本删除被拒绝，无运行依赖版本可显式删除且不会级联删除特征来源，重新安装后通过校验才恢复为可选目标。
- [ ] 新算法候选安装和全量迁移不会提前改变任何人员的线上特征状态；只有算法、特征引用和完整索引原子激活成功后，API 才展示新契约状态。
- [ ] 全量迁移有人员失败时，成功候选特征不会被丢弃或重复提取，候选一致性校验通过后自动切换；失败人员准确显示为 `has_face=true, feature_status=stale`。
- [ ] 激活前增量追平覆盖新增、换图、移除和删除；最终写屏障期间新索引写入收到稳定可重试响应，激活版本记录其截止水位且不会覆盖更晚照片或恢复已删除人员。
- [ ] 无失败迁移终态为 `activated`，有人员失败迁移终态为 `activated_with_errors`；两者都在候选一致性校验后自动激活并可跨重启查询，系统级失败不会切换旧版本。
- [ ] 最终写屏障前更换失败人员照片会更新原迁移任务并只重试对应人员；任务激活后换图使用当前新算法的普通异步操作，不会丢弃或重复提取其他成功特征。
- [ ] 零成功保护能区分“有注册照片但全部迁移失败”和“最终没有注册照片”；前者保持旧版本并返回稳定错误，后者可正常激活空索引。
- [ ] 并发更新、通信失败、事务回滚和服务重启均有一致性测试。
- [ ] 删除后重新创建相同 `person_id` 会产生新的内部记录和特征版本，旧历史引用保持不变。
- [ ] 显式移除人脸后人员保持存在且不参与识别；省略照片动作的普通更新不会误删现有人脸。
- [ ] 管理端可只读查询外部批次汇总和逐项失败结果；查询支持时间、批次状态、`person_id` 与项目状态筛选，不提供修改、重试或回滚批次的接口。
