# 人员管理功能

## Goal

为 AI 视频分析边缘平台提供独立于后台登录用户的人员底库管理能力，使管理员和外部业务系统能够维护可被人脸算法识别的人员及注册照片，并保证人员 API 返回成功时，数据库中的激活版本与 C++ 引擎实际使用的人脸索引一致。

用户价值：管理员可以先建立人员档案、再补录人脸，业务系统可以通过稳定的 `person_id` 幂等同步人员；人脸注册、换图和删除在成功返回后立即反映到识别行为中，失败时不破坏仍可用的旧人员版本。

## Background and Confirmed Facts

- 本任务以 `docs/prd/ai-video-analytics-edge-platform-v1.0.md` 的 7.8、8.3、10.4、11.4 为上位需求。
- 人员是人脸识别的业务对象，不是可以登录管理后台的 RBAC 用户。
- 当前仓库没有人员数据模型、人员 HTTP API 或人员管理前端页面。
- 当前 `engine/proto/aivision/v1/person.proto` 仅预留 `PersonService.SyncPersons`，handler 语义为 `UNIMPLEMENTED`；现有消息不包含注册图片、质量结果、特征字节、特征契约或候选/激活版本，不能直接满足本任务。
- 现有 macOS 人脸算法包任务只负责视频帧的人脸 embedding 输出，明确不负责图库管理、身份注册、1:N 搜索和人员业务管理。
- V1.0 目标规模为 10,000 人，每个人员只允许一张当前有效人脸照片。
- 每条人员记录使用数据库内部主键 `id` 做表关联和生命周期区分，`id` 不对管理页面或外部同步 API 暴露。
- `person_id` 是设备内当前有效人员唯一、创建后不可修改的业务主键，也是页面、同步命令和逐项结果使用的人员标识。
- 删除后用相同 `person_id` 重新添加会生成新的内部 `id`，不会与旧历史记录使用的内部身份混合。
- 本任务采用父任务统筹、三个子任务分阶段交付；只有跨子任务验收全部通过后，父任务才算完成。

## Delivery Structure

| 子任务 | 交付边界 | 依赖关系 |
| --- | --- | --- |
| `08-26-person-engine-index` | 注册图质量检测、特征提取、候选索引构建与原子激活 | 首先冻结引擎契约 |
| `08-26-person-data-api` | 人员版本事务、图片与特征持久化、管理 API、IP 白名单同步 API | 依赖引擎契约 |
| `08-26-person-ui-integration` | 人员管理页面、RBAC 菜单与权限、错误展示、端到端验收 | 依赖可用的管理 API |

父任务拥有上位需求、跨子任务一致性与最终验收；子任务分别完成设计、实现和质量检查，不把阶段性内部能力误报为可用的人员管理功能。

## Requirements

### R1. 人员身份与资料

- V1.0 人员资料字段固定为 `person_id`、姓名和当前人脸照片；需要使用工号时，由业务方直接将工号作为 `person_id`。
- 姓名为必填展示字段，但允许不同人员重名；姓名不参与唯一性判断、幂等匹配或同步结果关联。
- 页面新增人员时 `person_id` 可选；未提供时由平台生成，手工提供时校验设备内唯一。
- 平台生成的 `person_id` 与管理员手工填写的 `person_id` 具有相同业务语义；页面必须在提交前说明其创建后不可修改，并对重复值给出明确错误。
- 外部同步 API 必须提供 `person_id`，并以其实现幂等新增、更新和删除。
- `person_id` 创建后不可修改。
- 页面与外部同步 API 操作同一人员模型，后一次成功操作覆盖前一次结果。
- 管理页面和外部业务系统都是同一人员模型的合法写入方，不设置某一来源为人员数据的唯一权威方。
- 不持久化独立 `face_status`；是否已注册人脸以当前注册照片引用是否存在为唯一事实来源，API 按该关系派生返回 `has_face`。
- `feature_status=missing|ready|stale` 表示当前注册照片是否具有与当前激活算法包所要求 `feature_contract_id` 匹配的可用特征。无照片时固定为 `missing`；只有 `has_face=true`、`feature_status=ready` 且已进入当前激活索引的人员参与识别。
- 支持显式移除当前人脸；成功后当前照片引用为空、`has_face=false`、`feature_status=missing`，人员档案继续存在但立即停止参与识别。
- 算法包版本变化本身不使特征失效；只有目标算法包声明的 `feature_contract_id` 与特征记录不匹配时，该特征才变为 `stale` 并退出索引，不能参与相似度比较。
- 人员建档与人脸注册是两个独立原子操作；页面可连续执行，但不得把两者伪装成一个不可分割事务。
- 每个人员最多有一张当前有效注册照片；历史照片版本不可变。

### R2. 管理入口与权限

- 管理前端提供人员分页查询、新增、修改、删除和详情查看。
- 人脸管理挂载在人员管理之下：管理员从人员列表进入该人员详情，在同一详情界面完成补录、换图和移除人脸；不建立独立的人脸管理菜单、列表或路由。
- 页面路径、路由名和页面权限分别为 `/resource/person`、`ResourcePerson` 和 `resource:person`，位于“资源管理 -> 人员管理”。
- 页面使用现有 RBAC 菜单、接口和操作权限，不按预置角色在代码中写死权限。
- 人员资料与人脸维护统一使用 `resource:person:update` 权限；修改姓名、补录、换图和移除人脸不再拆分独立人脸权限。
- 新增人员、编辑人员和删除人员分别使用 `resource:person:create`、`resource:person:update`、`resource:person:delete`；同步白名单继续使用 `resource:person:sync-config`。
- “人员管理”页面提供独立“同步设置”入口，不新增一级或二级菜单；入口使用权限 `resource:person:sync-config`。
- 同步设置支持查看、新增和删除 IPv4、IPv6 单地址或 CIDR 白名单；无该权限的用户不可查看或修改配置。
- 管理页面新增、补录和换图使用浏览器本地文件选择，仅接受 JPEG/PNG，并在提交前展示预览。
- 已注册人脸的人员详情提供“重新提取特征”操作，复用 `resource:person:update`；该操作使用当前有效注册照片强制重新执行质量校验与特征提取，不要求管理员重新上传照片。
- 重新提取统一支持 `single|selected|all` 三种范围；范围只决定处理哪些当前照片，不限制操作属于维护还是算法迁移。三种范围都强制执行目标版本质量检测和特征提取，不得用历史成功处理指纹跳过。
- 每个重提取任务在创建时冻结明确的目标算法包版本和 `feature_contract_id`；可选择当前激活、候选或设备仍保留且可加载的历史算法包版本，页面提交前展示目标版本、影响人数并二次确认。
- 强制提取任务本身不切换全局算法。只有任务关联了明确的算法升级或历史版本回切计划时，目标契约不同才要求 `scope=all` 和增量追平，并在迁移完成后按既定自动激活规则切换；普通单人、选中或全量提取只更新目标版本特征。
- 重提取失败时，原特征只有在 `feature_contract_id` 仍匹配当前激活算法包要求时才继续服务；原特征本就不匹配的人员保持 `stale`。为非激活历史/候选版本生成的特征不会改变当前 `feature_status`，直到该版本真正激活。
- 三种范围均复用 `resource:person:update` 并异步执行，可查询总数、进度、成功数和逐项失败原因。
- 管理页面通过人员专用、JWT/RBAC 保护的上传入口提交照片，不复用通用 `/api/file/upload`，也不要求管理员填写 `photo_url`。
- 人员写操作接入现有操作日志；日志不得记录完整人脸图片或特征字节。

### R3. 外部业务同步

- 提供独立的单人员幂等同步 API，支持按 `person_id` 新增、换图/更新和删除。
- 单人员和批量同步均支持显式 `remove_face` 操作；普通更新中省略 `photo_url` 表示“不修改人脸”，不得隐式清除当前人脸。
- 创建操作以“当前不存在有效同 `person_id` 人员”为前置条件；页面和外部同步均不使用人员版本号或乐观并发字段。
- 同一字段采用后一次成功写入覆盖前一次结果；服务必须按字段更新，姓名写入不得覆盖人脸状态或照片引用，人脸异步激活不得回写旧姓名。
- 无照片建档和纯姓名修改同步返回；首次注册、换图、移除人脸和删除当前可识别人员均采用异步操作，避免照片下载、特征提取和完整索引重建导致 HTTP 超时。
- 单人员异步提交立即返回 HTTP `202 Accepted`、唯一 `operation_id` 和查询地址；调用方轮询获取最终结果。
- 外部单人员写请求必须提供调用方生成的唯一 `request_id`，平台以其作为请求级幂等键并持久化载荷摘要、关联 `operation_id` 和最终结果。
- 相同 `request_id` 与相同载荷重试时返回原同步结果或原异步 `operation_id`，不重复执行业务；相同 `request_id` 携带不同载荷时返回稳定冲突错误。
- 单人员异步操作复用批次作业的持久化状态与恢复机制，但对外保持单项目结果契约。
- 异步处理期间继续使用提交前的稳定状态和索引：首次注册期间仍无当前注册照片，换图仍使用旧人脸，移除或删除在新索引激活前仍保持原有效状态。
- 只有索引激活和数据库版本切换全部成功后，操作才标记成功并切换人脸状态；失败时旧状态和旧索引保持不变。
- 同一人员在管理页面、单人员同步和批量同步之间共享一个索引操作互斥边界；任一入口已有操作处于待处理或处理中时，不接受新的索引相关操作。
- 重新提取特征属于索引相关异步操作，受相同互斥和统一索引刷新协调器约束；处理期间旧特征继续服务，成功激活后才替换，失败时旧版本保持有效。
- 以候选版本为目标的 `all` 范围迁移在任一时刻最多运行一个，使用有界并发和可恢复进度；不得为每个人员分别重建完整索引，全部特征准备完成后才构建候选完整快照。
- 算法包安装后读取并校验其声明的特征提取契约。若目标 `feature_contract_id` 与当前激活契约相同，算法版本切换不强制全量重提取，可继续使用兼容特征；若不同，则必须先完成强制全量迁移。
- 不兼容契约迁移期间旧算法、旧特征和旧索引作为一个激活版本继续服务；目标算法身份、全量目标特征和新索引必须按同一版本边界切换，不能先启用目标算法再继续使用不兼容旧特征。
- 新装或选中的历史算法包及其 `feature_contract_id` 先登记为目标候选版本，不改变当前激活算法、人员 `feature_status` 或线上索引；迁移产生的新特征也只保存为候选版本。
- 候选算法满足激活条件后，平台将目标算法、目标特征引用和候选完整索引作为一个版本原子激活；激活成功后旧契约特征才变为 `stale` 并停止参与识别，候选构建或激活失败则继续使用完整旧版本。
- 全量迁移允许人员级提取失败；准备阶段以所有项目进入成功或失败终态为完成条件，成功候选特征必须保留，不能因少量失败而重新提取全部人员。
- 存在人员级失败时，候选索引只包含目标契约下成功人员；只要算法加载、契约校验、候选完整索引构建和一致性校验成功，平台仍自动激活新算法，不等待管理员确认。失败人员保留当前照片但 `feature_status=stale`，暂时退出识别，换图或重新提取成功后再进入新索引。
- 全量任务无人员失败时终态为 `activated`，存在人员级失败但已成功切换时为 `activated_with_errors`；页面和 API 必须展示失败人数、明细及人员退出识别的结果。
- 迁移尚未进入最终写屏障时，管理员为失败人员换图，将新照片版本作为原迁移任务的增量重试项，只重新处理该人员并复用其他成功候选特征；任务已经激活后再换图，则按当前新算法执行普通换图操作。
- 同一照片指纹的确定性质量失败不重复计算；照片版本变化或原失败属于可重试运行故障时允许重新处理。人员级失败不阻止自动激活，算法加载、契约、索引构建或原子切换等系统级失败则不得激活并继续使用旧版本。
- 零成功保护：最终增量水位仍存在至少一名具有当前注册照片的人员，但目标契约下 `ready` 特征数为 0 时，不得自动激活空索引，任务按迁移验证失败终止并继续使用旧版本；最终水位没有任何注册照片时，空索引是合法激活结果。
- 全量任务开始时冻结初始人员及其当前照片版本并记录数据库变更水位；初始任务统计保持稳定，迁移期间仍允许正常新增、换图、移除人脸和删除人员。
- 迁移期间所有影响当前人脸的成功操作必须写入持久化增量集合。候选激活前按每个人员最新照片版本追平：新增或换图提取目标特征，移除人脸或删除人员从候选快照排除；失败增量按人员级迁移失败处理。
- 最终激活使用短暂写屏障：先停止接受新的索引相关人员写入，追平截止水位内的全部增量，再构建并原子激活最终候选快照。屏障期间新请求返回稳定、可重试错误，不长期锁定人员或让旧照片候选覆盖新照片。
- 新请求返回稳定 `PERSON_OPERATION_IN_PROGRESS` 错误，并携带现有 `operation_id` 供查询；批量中仅对应项目失败且标记为可重试，其他项目继续处理。
- MVP 不对同一人员的索引操作排队，不支持取消、抢占或以新操作覆盖旧操作；前一操作终止后，调用方可重新提交。
- 进行中操作的互斥状态必须持久化并支持服务重启对账，不能因进程重启错误接受第二个并发操作。
- 图片下载超时、连接失败和 C++ 引擎暂不可用等暂时性故障在同一操作内最多自动重试 3 次，并使用退避间隔。
- 字段校验失败、人脸质量不合格、图片类型不合法或响应超限等确定性错误不自动重试。
- 自动重试沿用原 `operation_id`、`batch_id` 和批次内 `person_id`，不得重复建档或创建并行候选版本。
- 自动重试耗尽后操作进入终态失败；逐项结果保留稳定错误码并标记 `retryable=true`，由调用方决定是否使用最新状态重新提交。
- 提供批量人员同步 API，用于首次导入和大规模增删改；批量接口不能要求业务系统逐人触发全量索引重建。
- 同一业务批次中成功的人脸新增、换图和删除必须作为不可拆分的索引提交组，不得按人员分别重建全量索引；该组可以与其他已就绪提交组共同进入一次索引刷新。
- 批量同步逐项校验并允许部分成功；字段非法、照片不合格等项目返回独立失败结果，不阻塞无依赖的合法项目。
- 合法但会改变人脸索引的项目作为一个原子组提交；候选索引构建或激活失败时，该组全部回滚并返回失败。
- 不影响索引的合法建档和纯姓名修改不因索引组失败而回滚。
- 批量响应逐项返回处理状态与稳定错误码，使业务系统只重试失败项。
- 业务系统不负责生成或维护 `batch_id`；平台为每次批量提交生成唯一执行 `batch_id` 并在 HTTP `202` 响应中返回。
- 业务系统可以在修正部分图片后重新下发完整人员集合，不要求只挑选失败项，也不要求关联原批次。
- 每次完整重发形成新的不可变批次审计记录，但平台逐人比较当前资料状态和注册处理指纹；未变化项返回 `succeeded` 且 `changed=false`。
- 已成功且内容与注册契约均未变化的人脸不重复质量检测、特征提取或索引变更；此前失败项目只有在图片内容或注册契约变化时重新执行确定性处理。
- 原批次及逐项结果作为不可变审计记录保留；错误人员通过新的显式更新或删除纠正，不修改原结果。
- 平台持久化批次状态和逐项结果，并允许调用方按 `batch_id` 查询处理中、完成或失败状态。
- 人员管理页内提供只读“同步记录”视图，不新增独立菜单；管理员可查看外部批次的提交时间、来源 IP、状态与数量汇总，并按批次状态、时间范围和 `person_id` 定位逐项失败原因。
- “同步记录”复用人员页面查看权限；“同步设置”仍单独受 `resource:person:sync-config` 控制。MVP 不在同步记录中提供整批重试、回滚或修改原结果的操作。
- 批量同步采用异步作业模型；提交成功立即以统一 `{code,data,message}` 信封返回 HTTP `202 Accepted`，`data` 至少包含 `batch_id`、`status=accepted` 和状态查询地址。
- 每个批次输入项必须包含 `person_id`，同一批次内不得重复；重复属于批次结构错误，在创建异步作业前拒绝整个批次。
- 单个批次最多包含 10,000 个唯一 `person_id`，与 V1.0 单设备人员容量一致；超过上限时在创建异步作业和下载任何照片前整批拒绝。
- 接受 10,000 项不代表并发处理 10,000 张照片；下载、质量检测和特征提取必须使用平台受控的有界并发。
- 逐项结果直接以 `person_id` 关联原始项目，不要求业务系统额外生成 `item_id`，也不使用数组下标作为身份。
- 输入项可选携带 `client_ref`，平台在逐项结果中原样回传，供调用方关联自身行号或记录号；`client_ref` 不参与人员唯一性、幂等或处理顺序判断。
- 每个项目只描述该 `person_id` 的一个最终操作：`upsert` 或 `delete`。`upsert` 明确携带人脸动作 `keep|replace|remove`，不通过项目排列顺序表达多步修改。
- 批量请求是一组可大可小的显式命令，不是数据库全量镜像；业务系统可以下发全部人员，也可以只下发一个或部分人员。
- 人员未出现在某次批量请求中没有任何删除或停用语义；只有显式 `delete` 操作才能删除人员。
- 页面和业务系统可能交替更新或删除同一人员，平台只保证每次已接受操作、版本切换和索引激活的一致性，不承诺两个独立系统的数据自动双向收敛。
- `keep` 保持现有人脸；新人员没有现有人脸时维持 `has_face=false, feature_status=missing`。`replace` 必须提供 `photo_url`；`remove` 显式移除当前人脸。`delete` 不接受人脸动作。
- 批量项目通过局域网可访问的 `photo_url` 提供注册照片；平台在异步作业中下载图片后执行质量检测和特征提取。
- 平台为下载图片计算 SHA-256，并将图片摘要与 `feature_contract_id`、质量策略版本共同组成注册处理指纹；生产算法包版本仅作为审计来源，不参与兼容性去重，避免包版本变化但特征契约不变时无意义重提取。
- 同一人员的相同注册处理指纹已有成功结果时，本次项目返回成功但标记 `changed=false`，不重复质量检测、特征提取或索引变更。
- 相同注册处理指纹已有确定性质量失败结果时，可直接复用稳定失败结果；暂时性下载、网络或引擎失败不缓存为确定性图片结论。
- 图片 URL 字符串、文件名和 HTTP ETag 不能单独作为人脸内容未变化的依据；同一 URL 内容变化时必须按新 SHA-256 重新处理。
- 调用方可选提供 `photo_sha256` 以便平台在当前激活照片指纹明确匹配时提前判定无变化；平台实际下载新内容时仍需校验声明摘要，摘要不一致则项目失败。
- 批量同步不使用 `multipart/form-data` 暂存照片，也不允许在 JSON 中内嵌图片 Base64。
- 照片下载失败、超时、URL 失效、响应超限或文件类型不合法时，只将对应项目标记失败，并返回明确失败阶段和稳定错误码。
- MVP 下载器只实施协议为 HTTP/HTTPS、超时、最大响应大小和真实图片类型等基本运行保护，不实现复杂的图片目标访问策略。
- 调用方必须保证 `photo_url` 在该项目被处理前持续可访问；平台不得把下载到的原始响应正文写入日志。
- 批次汇总状态固定为 `accepted|processing|completed|completed_with_errors|failed`，并返回总数及待处理、处理中、成功、部分成功、失败、已回滚数量。
- 提供独立的分页逐项结果查询，支持按项目状态筛选；10,000 项结果不得要求一次性全部返回。
- 项目状态固定为 `pending|processing|succeeded|partially_succeeded|failed|rolled_back`。每项至少返回 `person_id`、可选 `client_ref`、操作类型、状态、处理阶段、稳定错误码、可展示消息、是否建议重试，以及由当前照片引用派生的最终 `has_face` 和最终 `feature_status`。
- `upsert` 的人员资料变更与人脸动作沿用独立原子语义；资料成功但人脸失败时项目为 `partially_succeeded`，并分别返回 `profile_result` 与 `face_result`，不得把已成功资料变更隐藏为整体失败。
- 处理阶段至少能区分请求校验、人脸质量、特征提取、索引构建/激活和完成，使调用方知道失败发生在哪一步。
- 批次和逐项结果不返回原始照片、特征字节或其他大体积敏感载荷。
- V1.0 批次完成状态和逐项结果仅由调用方轮询查询，平台不主动发送完成回调。
- 同步 API 使用默认拒绝的 IP 白名单；支持 IPv4、IPv6 单地址和 CIDR。
- 来源地址默认使用 TCP 真实连接地址，不信任 `X-Forwarded-For`。
- 白名单变更立即生效并写入操作日志。
- 运行时白名单持久化在数据库中并作为请求校验权威来源；默认空列表拒绝所有外部同步请求。
- 部署配置可用于设备首次初始化白名单，但初始化后不覆盖数据库中的运行时修改。
- MVP 只以调用方 IP 白名单作为外部同步认证条件；调用方通过白名单后，平台信任其提供的 HTTP/HTTPS `photo_url`，不再要求图片目标主机或网段进入另一套白名单。
- 外部同步认证机制必须保持可替换；后续新增 Token 认证时，不修改人员同步 handler 之后的业务规则、批次模型或逐项结果契约。

### R4. 注册照片准入

- C++ 推理引擎负责注册照片的人脸质量检测和特征提取。
- 注册图片必须且只能检测到一张人脸，并通过最小人脸尺寸、清晰度、姿态和遮挡等质量门槛。
- 管理页面单张照片默认上限为 10 MiB；服务端同时校验声明大小、实际读取大小和真实图片类型，不能只信任扩展名或请求 MIME。
- 页面照片上传被 HTTP 接受后进入既定异步人脸注册操作，不在上传请求内同步等待特征提取。
- 质量或特征提取失败时返回稳定、可展示的错误码。
- 首次人脸注册失败时保留人员档案，当前照片引用仍为空并维持 `has_face=false, feature_status=missing`，允许后续重新提交照片。
- 人员换图失败时保留旧照片、旧特征和旧索引；不得产生部分生效状态。

### R5. 特征与索引一致性

- 算法包清单必须声明特征提取器 ID/版本、模型内容摘要、预处理契约、输出维度与数据类型、归一化方式、相似度度量及声明的 `feature_contract_id`。平台按规范化字段和实际模型文件 SHA-256 重新计算不可变契约指纹，只有与声明值完全一致才允许安装或加载；算法包提取结果必须原样回传同一契约，否则结果无效。
- 人脸特征以 PostgreSQL `bytea` 持久化，并绑定生产该特征的算法包 ID/版本、特征提取器 ID/版本、模型摘要和不可变 `feature_contract_id`；不能只记录笼统算法版本。
- 已安装历史算法包默认保留且不自动清理，以支持历史版本强制提取和回切；管理员可显式删除没有运行依赖的版本，重新安装时必须重新通过完整契约和模型摘要校验。
- 当前激活版本、目标候选版本或任一待处理/进行中提取及迁移任务引用的算法包禁止删除。仅有历史特征生产来源引用时不阻止删除包文件，但特征记录继续保留不可变来源信息，并明确提示删除后无法再使用该版本提取。
- Go 将候选版本的全部有效人员特征快照发送给 C++，由 C++ 构建候选内存索引。
- 无照片建档和纯姓名修改不重建索引；首次人脸注册、换图、显式移除人脸、删除可识别人员或重新提取特征时构建候选新索引，构建期间识别继续使用旧索引。
- 人脸质量检测和特征提取成功后，索引相关操作先进入 `ready_for_index`，由统一索引刷新协调器合并提交，而不是每个操作立即重建全量索引。
- 外部业务批次是不可拆分的最小提交组；协调器可以把多个业务批次和单人员提交组合并到同一个候选索引版本，但不能拆开一个业务批次的合法索引项。
- 索引刷新采用可配置的“数量阈值或最长等待时间”策略：就绪变更达到数量阈值，或最早就绪提交组等待超过上限时，触发一次完整候选索引构建。
- `flush_count` 与 `max_wait` 属于运行平台/部署 Profile 参数，不在通用业务协议中写死。
- 第一组默认值先在 Apple Silicon macOS 环境通过固定人员规模与特征工件实测冻结，用于 macOS 开发 Profile 和协调器验证。
- `rk3576-rknn` 不继承 macOS 数值；在 RK3576 Profile 验收前必须使用目标板、目标运行时和目标特征工件独立实测并覆盖该 Profile 参数。
- 业务批次只有在其所有索引相关项目完成特征准备或进入终态失败后才成为“就绪提交组”；最长等待时间从提交组就绪时开始计算，不得因照片仍在处理而拆分业务批次。
- 大型业务批次完成照片与特征准备后作为一个提交组进入协调器，整个批次最多参与一次索引刷新，不能按数量阈值在批次内部切成多次全量构建。
- 单人员异步操作在等待合并期间保持处理中；只有其所在候选索引激活后才进入终态成功。
- 数据库候选版本与 C++ 候选索引全部成功后原子激活；人员 API 此后才返回成功。
- 构建或切换失败时废弃候选版本，旧数据库激活版本与旧内存索引继续有效。
- 服务重启只加载已激活版本，不能把未完成候选版本加入识别库。

### R6. 删除与历史引用

- 删除人员成功后，该人员立即退出有效人员库和内存索引，不再参与识别。
- 显式移除人脸只解除当前有效照片和特征，不删除人员；旧照片版本在停止参与识别后仍按历史引用规则保留。
- 删除后不提供恢复流程；允许以后重新使用相同 `person_id` 建立一条新的内部人员记录。
- 重新添加不会复用旧照片、旧特征或旧索引成员；如需参与识别，必须重新提交照片、提取特征并完成新索引激活。
- 历史抓拍、识别和候选记录保留 `person_id`、姓名等必要文本快照。
- 被历史记录引用的底库图版本继续可查看；最后一条引用解除后才允许物理删除。
- 图片物理删除由既有 C++ 图片生命周期边界按图片 ID 幂等执行，不向 C++ 传递任意文件系统路径。

### R7. 查询与容量

- 人员列表支持服务端分页，并至少支持按 `person_id` 和姓名筛选。
- 人员列表支持按派生字段 `has_face` 和 `feature_status` 筛选，并明确区分“未注册人脸”“有照片但未提取”“特征可用”和“特征已失效”。
- 设计和测试必须覆盖 10,000 名有效人员，不以一次性加载全部照片到页面作为正常交互方式。
- 列表页面启用路由缓存；重新激活时刷新服务端数据，同时保留筛选条件、分页和滚动位置。

## Out of Scope

- 后台登录用户、角色或部门管理。
- 人脸识别算法模型的研发与精度验收。
- 抓拍、识别、Top-K 候选记录页面和 Webhook 消费流程。
- 一个人员多张同时有效的人脸照片。
- 陌生人聚类、陌生人身份去重和考勤结果计算。
- 在产品代码中把图库管理或 1:N 索引职责塞入算法包。
- 独立的人脸管理菜单、页面或脱离人员档案存在的人脸记录。
- 独立工号字段、部门、联系方式、分组、标签、黑白名单和其他扩展人员属性。
- 管理页面中的文件批量导入和批量导出；外部系统批量同步 API 属于本期范围。
- 已删除人员恢复或撤销删除。
- 批次完成回调，以及回调鉴权、重试和投递记录。
- 外部批量同步的 multipart 照片暂存、`photo_token` 和 JSON Base64 图片模式。
- Token 认证、图片目标主机/CIDR 白名单和其他高级 URL 访问策略。
- 管理页面通过 URL、Base64 或通用文件上传接口注册人脸。
- 对已完成批次执行自动或无条件一键回滚；批量纠错使用新的显式操作。

## Acceptance Criteria

- [ ] AC1：管理员可以在 `/resource/person` 分页查询、新增、修改、换图、删除和查看人员详情；无相应权限的用户不能从菜单或直接 URL 访问。
- [ ] AC1a：具有 `resource:person:update` 的管理员可在人员详情中修改姓名并维护人脸；系统不要求额外的人脸操作权限。
- [ ] AC1b：新增、编辑、删除分别受 `resource:person:create`、`resource:person:update`、`resource:person:delete` 控制，前端入口与后端接口执行一致的权限检查。
- [ ] AC2：页面新增允许自动生成 `person_id`；外部同步必须提供 `person_id`；重复同步不会创建重复人员，且 `person_id` 创建后不能修改。
- [ ] AC2b：管理员可在页面填写现有业务标识，留空时由服务端生成；手工值冲突时创建失败且不会产生人员或人脸处理副作用。
- [ ] AC2a：所有人员必须具有非空姓名，但不同 `person_id` 可以使用相同姓名；重名不会被合并或拒绝。
- [ ] AC3：人员可在没有照片时创建并显示为“未注册人脸/未提取”，且不会进入候选索引；人脸注册 API 只有在质量检测、特征提取和索引激活完成后才返回成功，成功后显示为“已注册/特征可用”并可以参与识别。
- [ ] AC4：无脸、多脸、人脸过小、模糊、姿态超限、遮挡超限或特征提取失败返回稳定错误；首次注册失败保留未注册人员，换图失败不影响旧版本继续识别。
- [ ] AC5：人员新增、更新和删除期间旧索引保持服务；候选索引构建或激活失败不会造成数据库激活版本与 C++ 内存索引不一致。
- [ ] AC6：删除成功后人员立即停止参与识别且不能恢复；重新使用相同 `person_id` 时创建新的内部记录并重新提取特征，历史记录文本快照和仍被引用的旧底库图不被改写或提前删除。
- [ ] AC7：外部同步 API 默认拒绝所有来源，仅接受白名单中的 IPv4/IPv6 地址或 CIDR，且默认不信任 `X-Forwarded-For`。
- [ ] AC8：页面和同步 API 的人员写操作均进入操作日志，日志中没有完整图片、特征字节或其他大体积敏感载荷。
- [ ] AC9：10,000 人规模下分页查询、全量特征快照构建和原子索引切换具备可重复的功能与性能验证证据。
- [ ] AC10：外部系统可通过批量 API 同步多个人员变更，一批合法的人脸变更作为不可拆分提交组且最多参与一次候选索引构建；非法项逐项失败，索引组失败时该组共同回滚，合法纯资料项仍可成功，响应可定位每一项结果。
- [ ] AC11：平台为每次提交生成并返回 `batch_id`；业务系统完整重发相同人员集合时形成新批次，但资料和图片未变化的人员返回 `changed=false`，不重复提取特征或刷新索引。
- [ ] AC12：批次提交立即返回 `202`；调用方可用 `batch_id` 查询汇总，并以 `person_id` 分页定位所有失败或回滚项，获取稳定错误码、失败阶段和可重试标识；可选 `client_ref` 原样回传。
- [ ] AC13：管理员或业务系统可显式移除当前人脸，使人员保留为 `has_face=false, feature_status=missing` 并立即退出索引；普通更新省略 `photo_url` 时现有人脸保持不变，重新注册产生新的照片和特征版本。
- [ ] AC14：人员模型不暴露 `revision`；同字段后写覆盖，姓名与人脸状态使用字段级更新，异步人脸激活不会把期间成功写入的新姓名覆盖回旧值。
- [ ] AC15：所有影响人脸索引的单人员操作立即返回 `202 + operation_id`，可跨服务重启查询；处理期间旧稳定状态继续服务，成功后原子切换并递增版本，失败或超时不改变旧状态。
- [ ] AC16：同一人员已有待处理或处理中的索引操作时，页面、单人 API 和批量项目均不能启动第二个操作；响应可定位现有 `operation_id`，其他批量项目不受影响，重启后互斥仍有效。
- [ ] AC17：暂时性下载、网络或引擎错误按退避策略最多自动重试 3 次，确定性错误不重试；所有尝试保持相同操作标识且不产生重复副作用，耗尽后返回可重试终态失败。
- [ ] AC18：外部单人员写请求使用必填 `request_id`；同键同载荷重试复用原结果或操作，同键不同载荷冲突，服务重启后幂等记录仍有效。
- [ ] AC19：批次内重复 `person_id` 时整批不创建作业；每人仅有一个最终操作，资料成功但人脸失败时返回 `partially_succeeded` 及可独立判断的资料、人脸子结果。
- [ ] AC20：有 `resource:person:sync-config` 权限的管理员可在人员管理页维护 IP/CIDR 白名单，修改立即作用于新请求并写操作日志；默认空配置拒绝所有外部同步，无权限用户不能查看或修改。
- [ ] AC21：管理员可选择不超过 10 MiB 的 JPEG/PNG 本地文件进行补录或换图并预览；人员专用接口返回异步操作，不接受伪造类型、超限文件或通用上传结果绕过注册流程。
- [ ] AC22：单人员和多个业务批次的就绪索引变更由统一协调器按数量阈值或最长等待时间合并刷新；不会每添加一个人员就重建一次全量索引，也不会把一个业务批次拆成多次全量构建。
- [ ] AC23：macOS 实测证据冻结 macOS Profile 的 `flush_count` 与 `max_wait`；RK3576 使用独立实测值，通用协议和业务代码不包含任一平台的硬编码阈值。
- [ ] AC24：业务系统可在修正部分图片后完整重发所有人员；重复的成功人员不重新提取，确定性失败且图片未变化的项目复用原失败结论，图片或契约变化的项目正常重新处理。
- [ ] AC25：业务系统可提交全部或部分人员；请求中缺少某个现有人员不会改变该人员，只有显式 `delete` 才删除；页面与业务系统的写入都遵循相同版本与索引原子性规则。
- [ ] AC26：单批 10,000 个唯一 `person_id` 可被接受并异步受控处理；重复人员或超过 10,000 项时整批在产生下载、特征或索引副作用前被拒绝。
- [ ] AC27：有人员页面权限的管理员可在同页“同步记录”中按时间和批次状态查询批次汇总，并按 `person_id` 分页定位逐项失败原因；记录只读且不提供整批重试或回滚。
- [ ] AC28：管理员可对已注册人脸人员使用当前注册照片重新提取特征；操作异步且会真实执行提取，成功后原子替换目标版本特征，失败时只有匹配当前激活契约的旧特征仍可识别。
- [ ] AC28a：单人、勾选批量和一键全量使用同一强制提取语义，范围、目标算法包版本和算法激活计划相互独立；旧特征仅在匹配当前激活契约时可继续服务，不匹配特征保持 `stale`。
- [ ] AC29：管理员可对勾选人员或当前全部已注册人脸人员发起异步重新提取，看到目标契约、影响人数、进度和逐项失败；10,000 人任务使用有界并发且最多构建一次候选完整索引。
- [ ] AC29a：一键全量可选择当前、候选或可加载的历史算法包版本，均强制处理范围内每张当前照片且旧指纹不能跳过；只有关联明确升级/回切计划的全量任务会在完成后切换算法。
- [ ] AC30：算法包版本变更但 `feature_contract_id` 相同时不强制全量提取；契约变化时旧版本持续服务，只有目标算法、全量目标特征和候选索引满足激活条件后才原子切换，不出现不兼容特征空间混用。
- [ ] AC30a：平台按算法包规范化契约字段和实际模型文件摘要重算 `feature_contract_id`；声明不一致的包不能安装或加载，运行时返回不一致的提取结果不能持久化。任一兼容性字段变化都会产生新契约并触发全量迁移要求。
- [ ] AC30b：历史算法包默认保留且可选择；激活、候选或任务引用版本不能删除，无运行依赖版本可由管理员确认后删除且历史特征来源不丢失，重新安装必须重新校验。
- [ ] AC31：人员 API 和页面同时返回派生 `has_face`、特征状态及特征契约；当前激活契约变化后不匹配特征变为 `stale` 且不进入新索引。
- [ ] AC32：全量迁移存在人员失败时保留所有成功候选特征并生成仅含成功人员的完整候选索引；候选一致性校验成功后自动激活，失败人员变为 `stale` 且可通过换图或重新提取恢复，不要求全部人员重做。
- [ ] AC33：全量迁移使用固定初始快照和持久化增量追平；迁移期间完成的新增、换图、移除人脸和人员删除都按激活前最新版本进入或退出候选索引，最终短暂写屏障内不会发生旧照片覆盖新照片或已删除人员重新进入索引。
- [ ] AC34：无人员失败时任务自动激活并进入 `activated`；存在人员级失败时仍自动激活并进入 `activated_with_errors`，不要求二次确认，只有系统级候选构建或切换失败才保留旧版本。
- [ ] AC35：最终写屏障前更换失败人员照片只在原迁移任务内重试该人员，成功候选特征不重做；任务已激活后换图按当前新算法的普通异步操作处理。
- [ ] AC36：最终水位有注册照片但目标可用特征数为 0 时，迁移失败且旧算法/特征/索引继续服务；最终水位无注册照片时允许原子激活目标算法和空索引。

## Risks and Deferred Items

- 当前 C++ 引擎缺少注册图质量检测、特征提取、候选索引构建和原子激活的正式 gRPC 契约，需要在技术设计阶段定义有界图片请求、特征载荷限制、错误码和重启恢复语义。
- 当前 macOS 人脸包只定义视频帧 embedding 流水线，是否复用同一模型资产完成注册图提取需通过算法包/引擎职责设计确认；不能假设现有 `SyncPersons` 已实现该能力。
- 10,000 人全量索引重建的耗时、峰值内存和额外存储空间尚需实测并形成验收阈值。
- MVP 信任已通过调用方 IP 白名单的业务系统提供 `photo_url`，因此接受其可请求设备可达 HTTP/HTTPS 地址的风险；Token 认证与更细粒度 URL 访问策略延期，但下载超时、大小和图片类型保护不能省略。
