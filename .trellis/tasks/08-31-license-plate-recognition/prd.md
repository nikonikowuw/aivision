# 车牌识别与车辆通行记录

## Goal

在 Argus 现有“摄像头任务 -> Engine 算法实例 -> 结果回调与抓拍 -> Go 管理服务 -> Web 管理端”链路上，新增端到端车牌识别能力，使用户可以查询车辆通行记录和每次识别的结构化结果。

车牌识别首先是一条事实观测记录，不天然等同于告警。MVP 只保存符合质量要求的车牌识别记录；黑名单、白名单或其他规则告警属于后续阶段。

## Background

- Engine 已支持算法包安装、版本激活、任务实例、视频解码、抽帧、规则下发、异步结果上报、抓拍落盘和图片对账。
- 当前算法类型为 `object_detection` 和 `face_recognition`；其中识别类算法不声明 `alarm_type_id`，避免算法输出隐式绑定业务告警语义。
- SDK 已定义 `AV_RESULT_RECOGNITION = 3`，现有规范使用该结果类型传递人脸识别结果。车牌识别应复用识别类结果通道并扩展明确的车牌 schema，不新增语义重复的结果 kind。
- 当前 `AlarmEvent` / `DetectedObject` 和 `alarm_records` 面向单目标检测告警，只包含 label、confidence、bbox 和 track ID，不足以表达车牌号码、颜色、类型以及 OCR 置信度。
- 通行记录需要独立的数据生命周期、检索索引和权限控制；不能通过向 `alarm_records` 持续追加车牌专用字段实现。

## Product Principles

1. **观测与告警分离**：MVP 保存车牌识别观测；名单、策略和业务告警不属于本期范围。
2. **算法与业务分离**：算法包负责检测、OCR、跨帧融合和质量判断；Go 服务负责保存结构化识别结果。
3. **结构化契约**：需要查询和索引的车牌字段采用强类型契约，不用无约束字符串 map 代替。
4. **端侧稳定输出**：算法按轨迹融合多帧 OCR，达到稳定条件后输出，避免把逐帧抖动直接写入业务库。
5. **可信上下文补齐**：算法不自行生成摄像头、实例、算法版本、业务时间、图片路径等宿主字段，由 Engine 从运行上下文补齐。

## Requirements

### R1. 算法类型与安装契约

- 新增并端到端支持 `algorithm_type: "license_plate_recognition"`。
- `license_plate_recognition` 属于识别类算法，manifest 不声明 `alarm_type_id`；若声明则安装校验必须明确拒绝。
- manifest schema、SDK/CMake 校验、Engine 解析与 metadata 一致性检查、Go 上传校验必须使用同一允许集合和条件字段规则。
- 既有 `object_detection` 和 `face_recognition` 行为及 ABI 数值保持兼容。
- 首期车牌算法包为自包含单体包，在包内完成检测、矫正、OCR、跟踪和多帧结果融合；不依赖另一个算法实例的中间输出。

### R2. 车牌识别流水线

- 算法包至少完成车牌定位、透视/旋转矫正、字符识别、结果置信度计算、目标跟踪和跨帧文本投票。
- 支持中国大陆常见蓝牌、黄牌和新能源绿牌；具体字符规则、特殊牌型及模型能力必须在实现设计中明确。
- 算法只在识别结果满足可配置质量门槛并达到稳定帧条件后输出。
- 同一轨迹在可配置去重窗口内不得重复输出相同稳定结果；新轨迹或超过窗口后可形成新通行记录。
- 无法可靠识别的目标不得伪造车牌文本；低质量观测可在算法侧丢弃并通过指标统计，不写入通行记录。
- 算法配置至少支持：最低检测置信度、最低 OCR 置信度、稳定帧数、轨迹去重窗口、支持的车牌颜色以及是否保存车牌裁剪图。
- 复用任务级 ROI、Mask 和分界线规则；区域用于限定车道/出入口，分界线可用于形成进出方向。空规则保持不过滤。

### R3. 识别结果契约

- 正常车牌结果使用现有 `AV_RESULT_RECOGNITION`，JSON 顶层包含 `schema_version: 1` 和非空 `plates` 数组。
- 每个车牌结果至少包含：`track_id`、`plate_text`、`normalized_text`、`plate_color`、`plate_type`、融合后的 `confidence`、`ocr_confidence`、原图归一化 `bbox`，以及可选的 `vehicle_bbox`。
- schema 必须定义字符长度、枚举值、置信度范围、bbox 边界、数组上限、未知字段和 JSON 总大小的校验规则。
- 算法提交全景抓拍和车牌裁剪所需的归一化 ROI；JPEG 编码、文件命名、原子落盘与生命周期仍归 Engine。
- 安装自测继续使用 `AV_RESULT_SELF_TEST`，不写业务记录、不请求抓拍。

### R4. Engine 处理与上报

- Engine 校验车牌识别 JSON，拒绝非法 schema、非法 bbox、非有限数值、超限数组或超限结果，并记录稳定错误码和指标。
- Engine 为每个车牌观测生成全局幂等事件 ID，并从可信上下文补齐 instance、camera、algorithm、version、wall time 和 time sync 状态。
- Engine 新增结构化车牌观测 IPC 上报，不把车牌观测伪装成 `AlarmEvent`。
- 上报至少包含识别字段、全景图片引用和可选车牌裁剪图片引用。
- 复用现有固定容量异步 worker、帧 retain/release、原子落盘、ACK、重试和孤儿图片对账机制；IPC 阻塞不得阻塞算法 worker。
- Engine 重启或 IPC 重试不得导致 Go 端产生重复通行记录。

### R5. 通行记录持久化

- Go 服务新增独立 `plate_observations` 数据模型、迁移、repository、service 和 API，不修改 `alarm_records` 以承载车牌专用字段。
- 每条记录至少保存事件 ID、摄像头、实例、算法及版本、发生时间、时间同步状态、车牌文本及规范化文本、颜色、类型、两类置信度、track ID、bbox 和图片引用。
- `event_id` 是软删除语义下的唯一幂等键；重复 IPC 上报返回成功 ACK，不重复插入，也不重复触发策略。
- 必须支持按车牌号码、摄像头、时间范围、颜色、类型和置信度组合筛选，并按发生时间倒序分页。
- 车牌号码支持规范化后的精确查询；是否支持包含式模糊查询由数据规模和索引设计决定，但 API 语义必须明确。
- 全景图和车牌裁剪图通过受 RBAC 保护的后端接口读取，不能向前端暴露可遍历的本地文件路径。

### R6. MVP 范围

- MVP 只提供车牌识别结果的通行记录，不实现黑名单、白名单、关注名单、策略匹配或实时业务告警。
- 名单管理、告警策略及观测-告警关联属于后续阶段，不得成为 MVP 的验收前置条件。
- MVP 不直接控制道闸、门禁继电器或第三方停车系统。

### R7. 管理端体验

- 新增“车辆通行”业务入口，与普通检测告警列表分离。
- 通行记录列表显示发生时间、车牌号码、车牌小图、摄像头、颜色和置信度，并提供车牌、摄像头、时间、颜色、类型和置信度筛选。
- 详情页显示全景图、车牌裁剪图、识别字段、摄像头、算法版本和时间同步状态。
- 任务配置复用现有算法选择、参数 schema 和检测规则编辑能力，不另建一套任务系统。
- 所有车牌文本、长摄像头名称和错误状态必须在桌面与移动宽度下完整或按明确规则截断，不能与图片和操作控件重叠。

### R8. 权限、审计与数据治理

- 车牌列表、详情和图片读取使用独立 RBAC 权限点；未授权用户不能通过图片 API 绕过页面权限。
- 应用日志默认不得记录完整车牌号或抓拍路径中的敏感业务信息；诊断日志需要车牌时必须脱敏。
- MVP 暂不提供通行记录导出和名单维护，因此不把名单审计作为本任务验收项。
- MVP 不自动删除通行记录和抓拍图片；暂不设置自动清理策略。数据库容量、磁盘容量和人工运维方式需在部署文档中说明。
- API、数据库备份中的车牌数据按敏感数据处理，部署文档必须说明访问责任。

### R9. 可观测性与质量验证

- 指标至少覆盖输入帧数、检测车牌数、稳定输出数、低质量丢弃数、非法结果数、IPC 队列丢弃数、上报成功/失败数和各阶段耗时。
- 结构化日志携带 camera、instance、algorithm、frame 和 event 上下文，但不记录未脱敏完整车牌。
- 固定测试集至少覆盖白天、夜间、逆光、运动模糊、倾斜、遮挡、蓝/黄/绿牌、无牌车辆和多车牌画面。
- 精度、召回率、误识率、端到端延迟和资源占用阈值必须在模型及目标硬件确定后量化，不能仅以“页面可看到结果”验收。

## Acceptance Criteria

### A. 契约与算法包

- [ ] `license_plate_recognition` manifest 在 SDK、Engine、Go 上传校验中结论一致；无 `alarm_type_id` 合法，声明该字段明确失败，既有算法类型行为不变。
- [ ] 算法包可独立安装、自测、启停、热更新配置和卸载，不依赖其他算法包的模型或运行中间结果。
- [ ] `AV_RESULT_RECOGNITION` 车牌 schema 的正常、边界和非法样例均有契约测试，原有 face recognition schema 不回归。
- [ ] 固定视频/帧序列证明多帧投票可以稳定输出，同轨迹去重窗口内不会产生重复观测，低质量车牌不会伪造文本。

### B. Engine 与 IPC

- [ ] Engine 对合法识别结果生成结构化车牌观测、全局幂等事件 ID、全景抓拍和可选裁剪图；非法结果被拒绝且无文件或 IPC 副作用。
- [ ] IPC 慢、断开、重连、队列满和 Engine 停机测试证明算法 worker 不被上报阻塞，所有帧引用和图片均按契约释放或进入孤儿对账。
- [ ] 同一事件重试上报后 Go 端仅存在一条通行记录，策略也只执行一次。

### C. 后端业务

- [ ] 版本化迁移可正向执行和回滚，`plate_observations` 具有事件幂等约束和车牌、摄像头、时间等必要查询索引。
- [ ] 通行记录 API 支持车牌、摄像头、时间、颜色、类型和置信度组合查询，分页总数与筛选结果一致。
- [ ] 重复 IPC 上报仅保留一条通行记录，不触发重复副作用。
- [ ] 图片接口验证 RBAC、路径规范化和不存在场景，不能读取配置根目录以外的文件。
- [ ] MVP 不执行自动数据清理；记录和抓拍图片在服务重启后仍可查询和读取。

### D. 管理端

- [ ] 用户可完成“配置识别任务 -> 查看通行记录 -> 查看识别详情及抓拍”的完整流程。
- [ ] 通行列表和详情正确处理无裁剪图、低置信度和时间未同步状态。
- [ ] 页面权限和接口权限一致，未授权账号无法查看车牌文本或图片。
- [ ] 前端类型检查、单测和生产构建通过，关键列表与详情在项目支持的桌面和移动视口下无重叠或溢出。

### E. 质量与性能

- [ ] SDK consistency、Engine build/test/asan/lint、Go test/vet、前端 check/unit/build 按受影响范围通过。
- [ ] 在 Apple Silicon macOS 与代表性视频集上记录准确率、召回率、误识率、P95 端到端延迟、CPU/内存占用和可持续分析 FPS。
- [ ] 断流、模型推理失败、磁盘不足、IPC 不可用、数据库暂时失败和服务重启都有可观察、可恢复且不产生重复通行记录的验证证据。

## Out of Scope

- 直接控制道闸、门禁继电器或第三方停车系统。
- 停车计费、车位管理、车辆轨迹地图、区间测速和跨摄像头车辆 ReID。
- 将算法系统扩展为通用的“检测插件 -> OCR 插件”可编排 DAG。
- 首期批量导入导出、模糊车牌反向检索、以图搜车和车辆品牌/车型/颜色识别。
- 未经目标硬件和模型验证就承诺具体识别准确率或最大车速。

## Dependencies And Risks

- 首发平台固定为 Apple Silicon macOS，推理运行时为 Core ML；RK3576/RKNN 不属于本任务验收范围。
- MVP 不自动删除通行记录和抓拍图片；记录与图片保留周期暂不设置自动清理策略。数据库容量、磁盘容量和人工运维方式需在部署文档中说明。
- “现场摄像头、车速和端到端延迟”属于部署验收参数：摄像头分辨率/码率/帧率决定车牌在画面中的清晰度，车辆速度决定运动模糊程度，端到端延迟表示从视频帧采集到通行记录在管理端可查询的时间。MVP 不预设统一摄像头、车速或延迟门槛，实现阶段使用代表性视频集记录实际表现。
- 识别效果高度依赖现场分辨率、车牌像素宽度、快门、补光、安装角度、车速和遮挡，必须使用真实部署样本校准。
- 首期支持普通蓝牌、普通黄牌和新能源绿牌；警车、教练车、挂车、港澳车牌等特殊类型的支持范围待模型验证后另行确定。未支持或无法可靠识别时应显示明确的未知/未识别状态，不得伪造车牌号。
- 车牌属于敏感个人信息；权限、审计、日志脱敏和访问治理缺失时不得进入生产验收。
- 当前 `AV_RESULT_RECOGNITION` 的规范以 `persons` 为固定顶层字段，需要将其收敛为按 `algorithm_type` 区分的 schema，避免破坏既有人脸识别契约。
