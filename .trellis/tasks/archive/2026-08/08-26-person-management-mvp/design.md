# 人员管理 MVP 技术设计

## 1. 自动生成的 `person_id` 格式
当用户未提供 `person_id` 时，系统将自动生成去划线的 UUIDv4（32字符，例如 `123e4567e89b12d3a456426614174000`）作为默认的对外唯一标识。

## 2. 同步 API IP 白名单校验
使用 Gin Middleware 实现在应用层进行 IP 拦截。中间件在服务启动时使用已经校验的固定白名单（IPv4/IPv6、CIDR），请求到达时获取 `c.Request.RemoteAddr` 的 IP 部分进行严格匹配；配置修改需重启服务后生效，不提供运行时热更新。应用层校验可以与现有统一错误响应和路由中间件组合，并避免信任代理头。

## 3. 路由设计
分为两套隔离的路由组：
- **前端页面 API**：挂载在 `/api/person`，使用现有的 JWT Auth 中间件进行身份验证，支持 `person_id` 选填逻辑。
- **外部业务系统 API**：挂载在 `/api/v1/open/person`，使用 IP 白名单中间件保护。对于此组接口，强制要求客户端必须传入 `person_id` 用于幂等的增删改操作。

前端页面 API 沿用现有 `/api` 路由约定；仅开放给外部系统的契约使用 `/api/v1/open` 版本化前缀。

## 4. `person_id` 更新规则
`person_id` 是创建后不可变的对外标识。更新接口只允许修改人员的可变字段；请求体中的 `person_id` 不作为更新字段，系统不支持通过任何接口修改已有人员的 `person_id`。

## 5. 本期范围边界
本任务只实现人员基础文本信息管理和同步闭环，不实现人脸图片、质量准入、特征提取、特征持久化、索引构建或 C++ `PersonService.SyncPersons`。人员 gRPC 预留协议保持不变，后续人脸库任务需另行定义并验证跨进程契约。

## 6. 基础模型字段
Person 只包含以下业务字段：
- `id`：内部自增主键，仅用于数据库定位，不进入 API 响应。
- `person_id`：对外唯一且创建后不可变的标识。
- `name`：人员姓名，本期唯一可修改业务字段。

`created_at`、`updated_at` 和 `deleted_at` 复用 `BaseModel`。

## 7. 删除与恢复规则
人员删除采用软删除：删除后人员不出现在默认列表和有效人员库中，但数据库保留原记录及 `person_id`。`person_id` 在包含软删除记录的所有记录中保持唯一。

同步 API 或页面再次提交已软删除的 `person_id` 时，恢复原记录、清除 `deleted_at` 并更新 `name`，不创建新记录，也不改变内部 `id`。后续物理清理作为独立的数据保留和历史引用释放流程处理。

## 8. 对外资源标识
所有 Handler、Service、前端 API 类型和外部同步 API 均使用 `person_id` 作为资源标识；内部数据库 `id` 不出现在 URL、请求/响应 DTO、日志业务载荷或前端模型中。

所有 HTTP JSON 请求、响应字段沿用现有 camelCase 约定（`personId`、`personIds`、`createdAt`、`updatedAt`）；数据库列仍使用 snake_case（`person_id`、`created_at`、`updated_at`）。文档中的 `person_id` 表示领域标识，不代表 HTTP JSON 字段名。

页面 API 采用以下资源形式：
- `GET /api/person/page`
- `POST /api/person`：`person_id` 可选，省略时生成去划线 UUIDv4。
- `PUT /api/person/:person_id`：只更新 `name`，不支持修改 `person_id`。
- `DELETE /api/person/:person_id`：软删除人员。
- `DELETE /api/person/batch`：根据 `personIds` 批量软删除人员，仅供已认证的管理页面使用；请求至少包含一个 `personIds`。
- 本期不注册单人员详情查询路由；未来可在此资源下扩展 `GET /api/person/:personId`，不在本期实现。

## 9. 外部同步 API
外部业务系统只提供单人员 REST 操作，由调用方自行逐条处理批量同步：
- `PUT /api/v1/open/person/:person_id`：幂等新增或更新。不存在则创建，已软删除则恢复原记录并更新 `name`，存在则更新 `name`。
- `DELETE /api/v1/open/person/:person_id`：幂等软删除；重复删除视为成功。
- 请求体只包含 `name`，`person_id` 必须来自路径，不能通过请求体修改标识。
- 开放 `PUT` 成功返回公开人员 DTO（`personId`、`name`、`createdAt`、`updatedAt`），不返回内部 `id`；开放 `DELETE` 成功返回 `data: null`。
- 开放接口不提供批量同步接口，也不要求 JWT；请求必须通过 IP 白名单校验。

## 10. IP 白名单配置边界
本期白名单采用固定启动配置，不提供前端管理页面、白名单管理 API 或运行时热更新。配置在应用启动时加载，修改配置后需要重启 Go 服务才能生效。

配置来源沿用现有 `config.yaml` + `APP_*` 约定：

```yaml
open:
  person_sync_allowed_ips: []
```

启动时可使用 `APP_OPEN_PERSON_SYNC_ALLOWED_IPS` 覆盖配置文件值，多个地址使用逗号分隔。两种配置都只在服务启动时读取。

- 配置默认为空，即默认拒绝所有 `/api/v1/open/person` 请求。
- 配置支持 IPv4/IPv6 单地址和 CIDR，匹配 TCP 真实连接源地址，不读取或信任 `X-Forwarded-For`。
- 白名单配置本身不记录人员管理操作日志；开放接口的写操作仍沿用现有 `/api` 操作日志拦截机制。
- 这是相对 PRD 7.8.2“白名单修改立即生效并接入操作日志”的 MVP 范围调整；后续可独立增加持久化配置、管理权限和热更新。

## 11. `person_id` 校验规则
手工填写的 `person_id` 必须满足以下约束：
- 长度为 1～64 个 ASCII 字符；
- 首字符为字母或数字；
- 后续字符仅允许字母、数字、`_`、`-`、`.`、`:`；
- 服务端先去除首尾空格；空值在页面创建时触发自动生成，在开放同步 API 中直接拒绝；
- 空格、斜杠、控制字符及其他字符均拒绝；
- 大小写按原值保留，唯一性比较区分大小写。

自动生成的去划线 UUIDv4 满足该规则。路径参数和请求体中的标识使用同一套校验规则。

## 12. 姓名规则
`name` 不是唯一字段，允许不同人员使用相同姓名。保存前去除首尾空格，不能为空；最大长度为 64 个 Unicode 字符，并拒绝控制字符。

## 13. 列表查询
`GET /api/person/page` 支持以下查询参数：
- `page`：页码，沿用现有默认值和校验规则；
- `pageSize`：每页条数，沿用现有上限 100；
- `personId`：按完整 `person_id` 精确匹配；
- `name`：按姓名模糊匹配。

默认只查询未软删除人员，结果按 `created_at DESC, id DESC` 排序。

## 14. 创建与 upsert 冲突规则
页面 `POST /api/person` 与开放 `PUT /api/v1/open/person/:person_id` 的重复处理不同：
- 页面未填写 `person_id` 时自动生成；
- 页面填写已存在的有效 `person_id` 时返回稳定的 `person_id` 冲突错误，不覆盖现有姓名；
- 页面填写已软删除的 `person_id` 时恢复原记录并更新姓名；
- 开放 `PUT` 对不存在、有效和已软删除的 `person_id` 均执行幂等 upsert：不存在则创建，已软删除则恢复，存在则更新 `name`；
- 开放 `PUT` 的重复调用结果一致。

## 15. 删除语义
页面 `DELETE /api/person/:person_id` 对不存在或已软删除人员返回 `CodeNotFound`；开放 `DELETE /api/v1/open/person/:person_id` 对不存在或已软删除人员返回成功，以保证同步删除幂等。两者都只执行软删除，不物理删除数据库记录。

## 16. 页面菜单与权限
沿用 PRD 菜单契约新增资源管理下的人员管理页面：
- 路径：`/resource/person`；
- 路由名：`ResourcePerson`；
- 页面权限：`resource:person`；
- 图标：`ant-design:idcard-outlined`；
- 页面保持缓存，重新激活时刷新数据并保留筛选、分页和滚动位置。

页面操作权限拆分为 `resource:person:add`、`resource:person:edit` 和 `resource:person:delete`，分别控制新增、编辑和删除按钮。没有页面权限的用户不能通过菜单或直接 URL 访问页面。

页面支持多选批量删除，批量删除使用页面认证 API；请求体使用现有 JSON 命名风格的 `personIds` 数组，数量限制为 1～100。对已不存在或已软删除的项忽略，其他有效人员继续删除并整体返回成功，成功响应为统一格式中的 `data: null`。开放接口仍只支持单人员操作，不增加开放批量接口。

开放接口位于认证路由组之外，不使用 JWT 和页面权限，只执行固定 IP 白名单校验。

## 17. 并发写入
本期不引入版本号、`If-Match`、乐观锁或应用层显式锁。`person_id` 使用数据库唯一约束防止重复记录，人员写入使用普通事务；并发更新按数据库提交顺序处理，最后成功提交的请求覆盖前一个请求。

## 18. 错误码
页面新增遇到已存在的有效 `person_id` 时返回新增的 `CodePersonIDTaken = 1018`，并在 `zh-CN`、`en-US`、`zh-TW` 文案表中提供对应消息。该错误码不用于开放 `PUT`，因为开放 `PUT` 始终执行幂等 upsert。

## 19. IP 白名单拒绝
开放接口中间件从 TCP 连接的 `RemoteAddr` 提取真实 IP；不匹配白名单时立即终止请求，返回 HTTP 403、业务码 `CodeForbidden` 和统一响应体，不读取或信任 `X-Forwarded-For`。

## 20. 白名单配置校验
应用启动时解析并校验全部白名单项。任一项不是合法 IPv4/IPv6 单地址或 CIDR 时，服务启动失败；非法配置不得被忽略或降级为空列表。配置为空是合法值，表示默认拒绝全部开放接口来源。

## 21. 页面表单
新增表单展示可选的 `personId` 和必填的 `name`；编辑表单展示当前 `personId` 但将其设为只读，编辑请求只提交 `name`。服务端仍负责最终校验，前端校验不替代后端校验。

## 22. 页面列表展示
人员列表左侧提供多选框，展示 `personId`、`name`、`createdAt`、`updatedAt` 和操作列。操作列支持编辑、单个删除；顶部提供批量删除。由于本期不包含照片、部门和状态字段，页面不预留对应列。

## 23. 页面交互边界
不创建独立人员详情页，新增和编辑均使用弹窗表单。人员详情仅通过列表字段展示；后续增加照片、质量或特征状态后再评估详情页。

## 24. 标识大小写
`person_id` 按大小写敏感处理并按原值保存；例如 `EMP-001` 与 `emp-001` 是两个不同标识。同步 API 不自动转换大小写，数据库唯一约束和精确查询均保持大小写敏感。

## 25. 批量删除交互
未选择人员时禁用批量删除按钮；选择后显示包含选中数量的二次确认提示。选择范围仅限当前列表页，不跨分页保留。确认后调用批量接口，成功时清空选择并刷新列表；不在确认框中展开完整人员信息。

## 26. 删除记录与恢复入口
本期页面不提供已删除人员筛选、回收站或单独恢复按钮。默认列表只显示未软删除人员；外部系统通过相同 `personId` 的开放 `PUT` 恢复，管理员可通过新增表单再次填写原 `personId` 恢复。

## 27. 操作日志
人员页面和开放同步接口的写操作沿用现有 `/api` 操作日志中间件自动采集；开放接口请求没有 JWT 身份时记录空操作人信息。固定启动白名单没有运行时修改操作，因此不产生白名单变更日志。

## 28. 代码库现状备注
当前仓库已有预留的人员 gRPC 协议定义，但尚未发现人员管理的 Go 模型、Repository、Service、REST API 或前端页面实现。后续设计应复用现有认证、分页、响应、操作日志和前端列表页面模式。
